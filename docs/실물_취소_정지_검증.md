# 실물 취소·정지 구현과 검증

2026-09-23. 사용자 제공 MoveStop/CheckMotion 예제를 참고했다.
**실물 로봇에 명령을 보내 검증한 결과가 아니다.** 아래 구현·자동 검사와 현장 확인을 구분한다.

## 구현

취소 접수 → Action cancel → 별도 ROS 클라이언트의 MoveStop(stop_mode=2) → 기존 작업 코드 종료 → CheckMotion IDLE(0) → CANCELED.

취소 후 API 호출 전후에 검사해 다음 이동·그리퍼 I/O를 차단한다. 예외 처리 안의 자동 후퇴·그리퍼 열기도 차단한다. 기존 힘/순응 해제 호출은 허용한다. 이미 내려간 디지털 I/O를 되돌리거나 그리퍼의 독립 동작을 즉시 멈추는 기능은 아니다.

MoveStop이 성공해도 기존 작업 코드가 끝나고 IDLE까지 확인하지 못하면 정상 취소로 보고하지 않는다. 무응답·거부·알 수 없는 상태는 정지 확인 실패다. 기존 동기 이동 함수가 반환하지 않으면 해당 Action도 정상 취소 완료가 되지 않는다.

실물 취소 후에는 새 Action을 잠근다. 피크 보유 상태는 모름으로 취급한다. 현장에서 그리퍼·페그·기타 접촉과 피크 위치를 확인하고, 로봇 기동 전제(피크가 거치대에 있고 접촉이 해소된 상태)를 복구한 뒤 robot_controller를 재시작한다. 잠금을 풀기 위한 자동 이동이나 자동 그리퍼 열기는 하지 않는다. 다음 조율에는 관제 재등록이 필요하다.

## 로컬 드라이버 대조

- dsr_msgs2/srv/MoveStop: stop_mode=2는 Soft Stop, 응답 success.
- dsr_msgs2/srv/CheckMotion: status=0 IDLE, 1 INIT, 2 BUSY. 드라이버는 success를 true로 채우므로 status도 명시적으로 검사한다.
- 설치 소스의 move_stop 서비스는 일반 move_joint/move_line과 별도 callback group이다. 로봇 컨트롤러에서도 정지 클라이언트는 별도 Reentrant 그룹을 쓴다.
- DSR_ROBOT2 이동 반환은 성공 0/거부 -1인 기존 규약을 유지한다. 예제의 좌표·속도·자동 이동 순서는 복사하지 않았다.

## 설정과 빌드

로봇 PC에는 기존 dsr_msgs2 의존성이 설치돼 있어야 한다. 드라이버를 저장소에 복사하지 않는다.

```bash
source /opt/ros/jazzy/setup.bash
# 로봇 PC의 기존 두산 작업공간 setup.bash도 source
cd /tmp/tunio-web-registration-pr  # 실제로 체크아웃한 저장소 경로로 변경
colcon build --packages-select tunio_interfaces tunio_robot tunio_server
source install/setup.bash
```

robot.launch.py의 `cancel_stop_timeout_sec`(기본 5.0초), `cancel_stop_interval_sec`(기본 0.1초)은 실측 전 임시값이다. 정지 모드는 예제와 같은 Soft Stop(2)이다. 보호정지 해제·드라이버 정지 모드 변경은 자동 수행하지 않는다.

## 로봇 없는 자동 검사

실물 도메인과 분리하고 가짜 로봇도 같은 도메인에 따로 켜지 않는다.

```bash
export ROS_DOMAIN_ID=194
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
unset ROS_DISCOVERY_SERVER ROS_SUPER_CLIENT
colcon test --executor sequential --packages-select tunio_robot tunio_server
colcon test-result --verbose
```

대역으로 검증하는 항목:

- MoveStop mode=2와 BUSY→IDLE 확인.
- 실패·무응답·알 수 없는 상태·작업 코드 미종료를 성공으로 취급하지 않음.
- 동기 이동 도중 취소 이후 다음 이동·그리퍼 명령 차단.
- 정지 확인 뒤 CANCELED 및 실물 복구 잠금.
- 실제 ROS Action cancel 요청/Result 상태 왕복(dry_run, 실물 API 호출 없음).

## 로봇 담당과 현장에서 확인할 항목

1. 먼저 기타·거치대와 접촉하지 않는 기존 검증 경로에서 진행 중 취소를 확인한다. 안전 정지 수단을 사용할 수 있는 상태에서 담당자가 실행한다.
2. 취소 시각, MoveStop 응답, 이동 반환, CheckMotion(IDLE), Action CANCELED 시각을 기록한다. 실제 감속·정지 위치와 지연도 확인한다.
3. 취소 후 새 이동·그리퍼 열기·자동 복귀가 없는지 확인한다. 새 Action은 복구 필요로 거부돼야 한다.
4. 응답 지연/통신 장애는 가능하면 대역에서 재현한다. 정지 성공으로 표시되지 않는지 확인한다.
5. 페그 파지·힘 제어·발현 접촉 중 취소는 별도 현장 검증이 필요하다. IDLE은 접촉력 해소·안전 자세를 뜻하지 않는다. Soft Stop 및 그리퍼 상태가 기타에 미치는 영향은 자동 테스트로 검증할 수 없다.

웹 취소는 소프트웨어 정지 요청이며 안전 인증된 비상정지 회로를 대체하지 않는다.
