# 실제 로봇 이동 시험

`tools/work_motion_check.py`는 실제 두산 M0609에 연결하는 단계별 시험 도구다.
시뮬레이션인 `work_motion_test.py`와 다르다. 로봇 노드와 같은 소스 함수·YAML을
사용하고, 현재 관절값과 두산 `ikin`으로 실제 목표를 구한다. 설치된 이전
`tunio_robot` 대신 이 저장소의 `src/tunio_robot`를 읽는다.

## 실행

두산 브링업은 유지하고 `robot_controller`, `task_manager`, 다른 직접 조작 도구는
종료한다. 빈손·그리퍼 open 38mm·주변 물체와 비접촉인 상태에서 시험한다.
전환은 오른쪽 작업 자세(J1 -60~80도, J3 양수)에서 시작한다. 출발점까지 자동 이동하지 않는다.

```bash
cd /home/mook/tunio_ws
source /opt/ros/jazzy/setup.bash
source /home/mook/ws_cobot_pjt/ws_dsr/install/setup.bash
source install/setup.bash

# 연결 없이 사용 안내만
python3 tools/work_motion_check.py

# 실제 현재값과 두산 IK 조회. 팔 이동·그리퍼 명령 없음
python3 tools/work_motion_check.py --peg 6 --check-only

# 실제 오른쪽→왼쪽 전환 + 기존 페그 앞 하강
python3 tools/work_motion_check.py --peg 6 --execute

# 높은 전환까지만 시험하고 싶을 때
python3 tools/work_motion_check.py --peg 6 --high-only --execute

# 현재 자세/sol에서 고정 홈을 거치지 않고 거치대 상단으로
python3 tools/work_motion_check.py --scene holder --execute

# 현재 자세/sol에서 6번 발현 상단으로
python3 tools/work_motion_check.py --scene pluck --peg 6 --execute

# 실제 피크 집기 → 고정 홈 없이 이동 → 6번 줄 1회 발현
python3 tools/work_motion_check.py --scene pick-pluck --peg 6 --execute
```

연결 전과 단계 확인에서 `y`를 입력해야 진행한다. 기본 시험 배율은 1.0이며
`--speed-scale 0.5`처럼 조정할 수 있다(0 초과 1 이하). YAML의 배율을 대체하며
기존 TCP 속도 상한도 유지한다. `holder`, `pluck`는 각각 상단 접근점까지만 간다.
`pick-pluck`만 실제 피크 집기·발현을 한다. 페그 파지/회전·피크 반환은 하지 않는다.
새 역방향 전환도 수행하지 않는다.

`--check-only`도 실제 로봇에 연결해 TCP/툴을 설정·조회하고 모드 전환을 수행한다.
완전 미연결 모드는 옵션 없이 실행하는 경우뿐이다.

## 하강과 충돌 진단

사용자 확인에 따라 기존 하강 좌표·동작은 유지한다. 기본 전환 시험도 하강을 포함하며,
하강 직전에 별도 `y` 확인을 받는다. 6·5번의 기존 접근점은 지정 빨간 박스와 겹친다.
시뮬레이션에서는 RG2와 TCP 침범이 확인됐으며 이 진단을 없애거나 안전 판정으로
바꾸지 않는다. 이 실기 도구에는 실시간 메시 충돌 검사가 없다.

## 중단·기록

단계 확인에서 거부하거나 예외/Ctrl+C가 나면 후속 이동을 보내지 않고, 실행 중이었다면
별도 ROS 클라이언트로 Soft Stop(mode=2)을 요청하고 CheckMotion IDLE을 확인한다.
5초 안에 확인되지 않으면 정지 확인 실패를 표시한다. Ctrl+C 처리는 Python으로
제어가 돌아와야 하므로 즉시 정지를 보장하지 않는다. 즉시 정지는 펜던트를 사용한다.
중단 후 자동 홈 복귀나 그리퍼 열기는 수행하지 않는다. 이동 전용 시험은 J6 회복도
수행하지 않는다. `pick-pluck`는 공통 집기·발현 함수의 기존 J6 회복 처리를 유지한다.

현재값·다음 단계·계획·실패 사유·정지 확인 결과는 각 단계 전에
`~/.tunio/robot_data/*_work_motion_check.json`에 저장한다.
중간에 다른 조작기로 팔을 움직였다면 도구를 종료하고 현재 자세에서 다시 계획한다.

로봇 연결/실제 이동은 개발 중 실행하지 않았다. 기본 미연결, 잘못된 입력 거부,
확인 거부 시 후속 명령 차단, 선택적 상단 종료와 공통 함수 호출은 대역으로 검사했다.


## 2026-09-29 첫 실기 실패 원인

컨트롤러 로그 `ros2_control_node_33149_1790645851237.log`의 첫 movej 직후
알람 1207: `JNT(5) POS LIMIT ERROR - INPUT(136.459), MAX(135.000)-MIN(-135.000)`.
접기 목표 J5=136.459도가 실제 설정 ±135도를 초과했다. 높은 접근점의
J5=-141.7195도도 한계 밖이다. 기존 시뮬레이션의 메시 충돌 통과가 이 현장
컨트롤러 제한 통과를 뜻하지 않는다. 당시 현재 관절은 이미 standby와 같아서
홈 이동을 추가하는 것만으로는 고칠 수 없었다. 컨트롤러 제한은 변경하지 않았다.

정지 확인 타임아웃에는 도구의 별도 오류도 있었다. 탐색용 `spin_once`가 기본
executor로 노드를 옮겨 정지 응답용 executor를 비웠다. 같은 명시적 executor로
탐색하도록 수정하고 ROS 노드가 실제로 남는 회귀 검사를 추가했다.
미도달 오류에는 movej 반환값·목표/실제 관절값·최대 오차를 기록한다.


### 경로 수정 및 재검사

접기 J5를 136.459→130도로, 왼쪽 높은 접근점 Z를 현재 높이+75 대신 250mm로
수정했다. 기존 페그 접근 XY/방향·하강 끝점은 유지한다. YAML의
`motion.peg_transition_left.high_tcp_z_mm`과 `controller_j5_limit_deg`에 기록했다.
실제 두산 IK가 반환한 상단·하강 목표와 모든 관절 경유점의 J5를 첫 이동 전에 검사한다.
기존 임의 소프트웨어 130도 제한을 복원한 것이 아니라 알람에서 확인한 ±135도다.

6·5번 각각 홈/거치대 출발, 상단/하강 포함 총 8경로를 0.5도 간격 검사했다.
상단 4경로는 팔·RG2 박스 충돌/자기 충돌/TCP 침범이 없고, 하강 포함 4경로는
기존 RG2/TCP 박스 중첩이 그대로 남는다. 자기 충돌은 없었다.
전환 및 하강의 수치 J5 범위는 6번 -134.083~130도, 5번 -134.821~130도다.
5번은 음수 한계 여유가 약 0.18도로 좁아 실제 컨트롤러 IK 사전 검사가 필요하다.
결과: `docs/simulation/work_motion_j5_checks.json`.
`colcon test --packages-select tunio_robot`: 439개 통과. 실물 재실행은 하지 않았다.

같은 명령 `python3 tools/work_motion_check.py --peg 6 --execute`로 수정 소스와 YAML을
바로 사용한다. 이 독립 도구에는 colcon 재빌드가 필요 없다. ROS 노드 적용에는
패키지 재빌드 및 노드 재시작이 필요하다.

2026-09-29 증속 요청: 일반 이동 배율 2.0→2.2, 시험 기본 배율 0.2→0.22로
각각 10% 올렸다. TCP 목표 속도/가속도는 본 코드 220mm/s·220mm/s²,
시험 도구 22mm/s·22mm/s²다. 관절/TCP 상한과 접촉·발현·페그 회전 속도는 유지한다.

후속 사용자 요청으로 시험 기본 배율은 1.0으로 변경했다. 시험 TCP 목표 속도와
가속도는 100mm/s·100mm/s²다. YAML의 일반 이동 배율과 별개로 적용한다.


## 2026-09-29 거치대·발현 상단 이동의 첫 상승 거부 수정

11:24 holder / pluck 실행은 `--execute`와 단계 확인이 정상적으로 진행됐지만,
첫 Z=299mm 수직 상승 목표에서 컨트롤러 알람 1206 NOT REACHABLE로 거부됐다.
실제 IK 기록의 J5=-137.0288도가 현장 ±135도 한계를 넘었다. 이동 속도나 확인 입력
문제가 아니다. 앞선 페그 전환 경로의 수정이 이 공통 복귀 함수까지 반영되지 않았다.

`_transfer_above_floor`를 수정해 왼쪽은 먼저 Z=250mm, 오른쪽은 Z=245mm까지
현재 방향으로 수직 상승한다. 다음 관절 이동에서 방향 변경과 추가 상승을 함께 해
최소 Z=320mm의 자세 변경점으로 간 뒤 목적지 상단으로 이동한다. 이미 높은 곳에
있으면 첫 단계에서 낮추지 않는다. J1/현재 sol 유지와 기존 접촉 좌표는 그대로다.

조정값은 `motion.work_orientation_raise_z_mm`,
`motion.work_orientation_raise_z_right_mm`, `motion.work_orientation_pivot_z_mm`이다.
현장 한계 `motion.controller_j5_limit_deg`는 공통 설정으로 옮겼으며, 페그 접근과
높이 이동 모두 시작·목표 관절을 첫 이동 전에 검사한다. 목표 미도달에는 실제/목표
TCP와 관절값을 출력한다. 정지·상태 확인이나 컨트롤러 한계를 우회하지 않는다.

실패 시 기록한 실제 6번 출발각으로 holder / pluck을 재현하고, 교시 좌표에서
6·5·2·1번의 두 목적지까지 총 10경로를 0.5도 간격 검사했다. 첫 상승 이후 자세 변경·
이동은 박스/자기 충돌 및 TCP 침범 0건이며 수치 J5는 ±135도 안이다.
**전체 경로에는 기존 페그 앞 출발·수직 이탈의 RG2/TCP 박스 중첩이 남는다.**
2번과 5번은 J5 여유가 각각 약 0.27도와 0.18도로 좁아 실제 IK 검사 결과가 우선이다.
원자료는 `docs/simulation/work_motion_exit_checks.json`.
446개 회귀 검사 통과. 실행기 소속 검사는 외부 ROS 노드 탐색에 의존하지 않게 했다.
이 기록은 실제 로봇 재실행 성공을 뜻하지 않는다.

같은 명령 `python3 tools/work_motion_check.py --scene holder --execute`로 재시도한다.
이 독립 도구는 소스·YAML을 직접 읽으므로 재빌드가 필요 없다. 시험 배율은 1.0이며
사용자가 수정한 작업공간의 일반 이동 배율 2.5는 유지했다.


## 실제 집기 → 홈 생략 → 1회 발현

```bash
python3 tools/work_motion_check.py --scene pick-pluck --peg 6 --execute
```

두산 브링업만 유지하고 통합 제어 노드·다른 조작 도구는 종료한다. 시작할 때 빈손이며
피크는 거치대에 있어야 한다. 6·5·2·1번 중 `--peg`로 발현할 줄을 선택한다.
시험 배율 1.0은 일반 이동에만 적용하며 접촉·발현 스트로크의 기존 속도는 유지한다.

확인은 세 작업 단위로 받는다. 작업 중간의 관절점마다 멈춰 묻는 모드는 아니다.

1. 거치대 상단 이동 → 그리퍼 열기 → 집기점으로 하강 → 닫기 → 상승.
2. 피크가 들렸는지 눈으로 확인한 뒤, 고정 홈 없이 현재 sol로 발현 상단에 이동.
3. 선택한 줄로 하강 → 한 번 발현·즉시 후퇴 → 발현 상단으로 상승.

로봇 노드와 같은 `pick_up(height_transfer=True)` 및
`pluck_string(height_transfer=True, prepare_only=True / prepared=True)`를 사용한다.
마이크 측정이나 페그 등록은 하지 않는 독립 동작 시험이다. 발현·즉시 후퇴 사이에는
확인 대기를 넣지 않는다. 끝나면 **피크를 든 상태로 발현 상단에 남는다**.
자동 반환·홈 복귀는 없다. 빈손 시험이므로 피크를 든 채 같은 시험을 재실행하지 않는다.

집기 성공은 자동 판정하지 않으며 기록도 `held_assumed`다. 놓치면 되찾을 수 없고
이후 발현도 실패하므로, 두 번째 확인에서 중단한다. 오류/확인 거부/Ctrl+C의 후속
명령 차단과 Soft Stop·IDLE 확인은 기존 도구와 같다. 이후 접촉·파지 상태는 직접
확인해야 하며, 자동 복구 동작은 없다.

`--check-only`는 이동·그리퍼 조작 없이 현재 자세에서 거치대 상단까지의 경로만
조회한다. 집기 후의 발현 경로는 실제 당시 관절값으로 별도 계획한다. 이 조회를
전체 집기·발현 경로의 충돌 검증으로 해석하지 않는다. 기존 박스 중첩도 유지된다.
실물 실행은 개발 중 수행하지 않았다. 대역 장치에서 공통 함수를 실제로 호출해
그리퍼 open/close, 준비 후 1회 스트로크·후퇴, 홈 미호출과 확인 취소를 검사했다.

추가 후 `colcon test --packages-select tunio_robot`: 453개 통과(로봇 미연결).
