# 로봇 앞에서 할 일 — 순서대로

로봇을 쓸 수 있을 때만 할 수 있는 작업을 모았다. **순서가 중요하다.**
앞 단계가 바뀌면 뒤 단계 측정값이 무효가 되는 관계가 여럿 있다.

- 대상: tunio_robot (페그 조절). 발현·화음은 성현 몫이라 여기 없다
- 기준일 2026-09-19
- 값을 얻으면 `src/tunio_robot/config/teach_points.yaml` 에 적는다

---

## 시작 전에

**마이크가 있어야 하는 단계가 있다 (5·7단계).**
`tools/peg_cal.py` 가 주파수를 재야 하는데 이 PC에는 `sounddevice` 가 없고
내장 마이크뿐이다. 외장 마이크와 `sounddevice` 설치가 필요하다.
없으면 5·7단계는 건너뛰고 나머지를 먼저 한다.

**처음 `dry_run:=false` 로 켜는 것이다.** 지금까지 로봇을 움직여본 적이 없다.
비상정지 위치를 먼저 확인하고, 속도는 YAML 기본값(5 deg/s)으로 둔다.

```bash
ros2 run tunio_robot robot_controller --ros-args -p dry_run:=false
```

## 1단계 · 그리퍼 배선 확인 (10분)

**이게 맞아야 아래가 전부 성립한다.** 로봇의 디지털 출력 번호가
Compute Box 의 입력 번호와 같다고 가정하고 코드를 짰다. 확인한 적은 없다.

하나씩 켜보고 그리퍼가 어떻게 되는지 본다.

- 출력 1번만 1 → **15mm 로 닫혀야** 한다
- 출력 2번만 1 → **90mm 로 열려야** 한다
- 출력 3번만 1 → **21mm** 여야 한다

다르면 번호 매핑이 어긋난 것이다. `teach_points.yaml` 의
`gripper.presets.<이름>.outputs` 를 실제 번호로 고친다.

기록: 어느 출력이 어느 폭인지

## 2단계 · 파지 폭과 깊이 확정 (20분)

```bash
python3 tools/peg_grip_check.py --peg 6
```

경유지 → 접근점 → 페그 순으로 자동으로 간다. 단계마다 확인을 받는다.
처음 한 번은 팔 자세(sol)를 모르니 `--jog` 로 사람이 옮겨서 값을 받아 적는다.


### 폭

21mm 로 6번 페그를 실제로 물어본다.

- 잘 물리면 그대로
- 헐거워 미끄러지면 웹에서 20mm 로 줄인다
- 안 들어가거나 빗나가면 22mm 로 늘린다

> 직접교시 옆 방향 오차가 실측 1.08mm 다. 한쪽당 여유가 0.5mm 면 그걸 못 덮는다.
> 헛잡으면 폭을 **늘리는** 쪽이 먼저다.

웹에서 값을 바꿨으면 `teach_points.yaml` 의 `gripper.presets.peg.width_mm` 도 고친다.

### 깊이

지금 페그마다 깊이(그리퍼가 다가가는 방향, 왼쪽은 Y 음수쪽·오른쪽은 Y 양수쪽)가
제각각이다. 교시할 때 손으로 밀어넣은 정도가 매번 달라서 생긴 차이지
페그 배치 차이가 아니다. 실측 편차가 6.6mm 였다.

**한쪽에 하나씩 정해서 네 페그에 같은 값을 쓴다.**

- 너무 얕으면 페그 끝에서 미끄러진다
- 너무 깊으면 헤드스톡이나 페그 몸체에 부딪힌다

현재 값: 왼쪽 6번 -75.38 / 5번 -77.07, 오른쪽 1번 59.88 / 2번 57.50

기록: 왼쪽 깊이 1개, 오른쪽 깊이 1개 → 네 페그의 Y 를 그 값으로 통일

## 2.5단계 · 좌우 전환 검증 (15분)

한쪽 페그에서 반대쪽으로 넘어갈 때 기타나 주변을 안 치는지 본다.
**페그를 잡지 않는다. 이동만 한다.**

```bash
python3 tools/transit_check.py --from 6 --to 1
```

한 구간 가고 멈춘다. 보고 괜찮으면 다음 구간. 아니다 싶으면 `n` 이나 Ctrl+C.

파지보다 이쪽이 더 위험하다 —

- 왼쪽 B=+90, 오른쪽 B=-90 이라 **손목이 180도 뒤집혀야** 한다
- TCP 가 208mm 라 그 뒤집힘에 손끝이 **반경 20cm 짜리 호**를 그린다
- 이동 중에는 그리퍼가 열려 있어(90mm) **폭도 제일 넓다**

### 경유지 값을 잡는 법 — 계산하지 말고 조그로

계산으로 잡기 어렵다. 직접 가보고 "이 정도면 안 걸리겠다" 싶은 자리에서
관절값을 읽는 편이 확실하다.

⚠️ **드라이버를 켜면 직접교시(손으로 밀기)가 안 된다** (2026-09-19 확인).
드라이버가 붙으면 로봇이 자동 모드로 잡힌다. 둘 중 하나만 된다.
그래서 손으로 미는 대신 **ROS 로 민다.**

```bash
python3 tools/jog.py --speed 20       # 관절을 조금씩 밀면서 값 읽기
```

`1 -20` 처럼 관절 번호와 각도를 친다. 움직인 뒤 관절·손끝·sol 을 바로 찍는다.
`u` 로 직전 이동을 되돌리고, `m` 으로 지금 자세를 후보로 적어둔다.
`go 6` / `go 1` 로 페그 접근점까지 한 번에 갈 수 있어, 실제 출발·도착
자세에서 시작해 볼 수 있다. 끝낼 때 yaml 에 붙여넣을 조각을 찍어 준다.

드라이버를 끄고 펜던트로 직접교시를 하는 쪽을 택했다면, 값은 펜던트 화면에서
읽으면 된다. 읽기만 하는 도구도 있다 (로봇을 안 움직인다) —

```bash
python3 tools/pose_read.py --watch    # 계속 보기
python3 tools/pose_read.py --watch --topic   # 서비스가 막힐 때 joint_states 로
```

⚠️ **J1 만 바꾸면 들어올리기가 빠진다.** J2·J3 를 null 로 두면 팔 높이와
뻗은 길이가 그대로라, 페그 높이 그대로 옆으로 쓸고 간다. 두 접근점이 둘 다
Z 약 113, 반지름 약 364mm 라 그 호에 헤드스톡이 걸린다.
원래 `[90, 0, 0, ...]` 이 안전했던 건 J2·J3=0 이 팔을 세워 기타보다 높이
올리기 때문이다. 휘두르는 게 핵심이 아니라 **들어올리는 게 핵심**이다.

걸리는 데가 있으면 `routes.transit.j` 에서 `null` 을 값으로 바꾼다.

- 높이가 모자라면 **J2·J3** 를 올린다 (제일 흔한 경우)
- 손끝이 기타를 쓸면 **J5 를 묶어** 안전한 데서 뒤집게 한다

처음 가보는 경로는 `--speed 30` 으로 보고, 괜찮으면 기본값(100)으로 다시 봐서
확정한다. 빠르게 움직이면 경로가 미세하게 달라진다.

### 2026-09-19 1차 결과 — 경유지는 통과, 접근 자세에서 걸림

6 → 경유지 → 1 이 **기타를 안 치고 지나갔다.** 경유지 자체는 문제가 없다.

```
출발점(6번)  관절 [125.1, -51.8, -87.9,  46.6, -120.7,  29.1]
경유지        관절 [ 90.0,   0.0,   0.0,  -0.0,    0.0,  29.1]   손끝 Z 1243mm
도착점(1번)  관절 [ 52.5,  51.4,  87.9, 134.2, -120.9, -28.0]
```

남은 문제 둘 —

1. **1번 접근 자세에서 J5 쪽 손목 케이싱이 바깥으로 뻗어 부딪힐 뻔했다.**
2. 페그에서 60mm 는 너무 붙는다. → `motion.approach_mm` 을 **100mm** 로 올렸다.

### 손목 케이싱이 걸릴 때 — 팔 자세(sol)를 바꾼다

같은 손끝 좌표라도 역기구학 해가 8가지다. 그중 **손목 뒤집기** 갈래는
J4 를 180도 돌리고 J5 부호를 뒤집는데, **손끝이 하나도 안 바뀐다.**
축 원점까지 똑같고 L자 케이싱 방향만 정반대가 된다.
(link_4 무게중심이 자기 축에서 146mm 벗어나 있어 실제로 크게 휜다)

1번 접근점 예 — 위는 지금, 아래는 뒤집은 것. 손끝은 같다.

```
[52.5, 51.4, 87.9,  134.2, -120.9,  -28.0]
[52.5, 51.4, 87.9,  -45.8,  120.9,  152.0]
```

어느 sol 번호가 그 해인지는 로봇에게 물어본다. **안 움직인다.**

```bash
python3 tools/sol_check.py --peg 1           # 8가지 해를 전부 찍어 준다
python3 tools/transit_check.py --from 6 --to 1 --dst-sol <번호> --speed 30
```

`sol_check.py` 는 L자 케이싱이 부푼 자리까지 찍고, 못 쓰는 해를 걸러 준다 —

- 어깨팔꿈치가 베이스 면(Z=0) 아래로 가는 해는 받침·책상을 파고든다
- 경유지 J1 에서 100도 넘게 돌아야 하는 해는 가는 길이 기타를 쓴다

### 1번 페그 결과 (2026-09-19) — sol 2

8개 중 0·1·4·5 는 어깨팔꿈치가 베이스 아래 127mm 로 내려가 탈락,
6·7 은 J1 이 −124 라 경유지(90)에서 214도를 돌아야 해서 탈락. 남은 건 2·3.

```
6번 (문제없었음)       케이싱 [191.2, -398.8, 146.1]
1번 sol 3 (부딪힐뻔)   케이싱 [375.7,  426.9, 238.4]
1번 sol 2 (손목 뒤집기) 케이싱 [207.4,  426.6, 141.7]   <- 6번과 거의 같은 자리
```

sol 3 은 케이싱이 6번보다 X 로 185mm 더 나오고 92mm 높다. 그게 걸린 것이다.
sol 2 로 바꾸면 6번에서 문제없던 자세의 거울상이 된다.

괜찮으면 `teach_points.yaml` 의 `pegs.<번호>.sol` 에 적는다.
**null 로 두면 그때그때 현재 자세를 따라가서 매번 달라진다.** 반드시 박아둘 것.

기록: 경유지 최종값, 각 페그의 sol, 걸리는 구간이 있었는지

### 팔 모양(sol)은 도구가 알아서 고른다

`pegs.<번호>.sol` 이 비어 있으면 로봇은 **그때의 현재 자세를 따라간다.** 그런데
경유지가 특이점 자세라 그 값이 모호해서, 같은 좌표로 가도 갈 때마다 팔 모양이
달라진다. 2026-09-19 회전 확인에서 실제로 이것 때문에 경유지→6번 접근점 경로가
순회 때와 달라져 부딪힐 뻔했다.

그래서 `transit_check` · `peg_grip_check` · `peg_turn_check` · `peg_tour` 넷 다
`arm_pose.choose()` 로 8가지를 받아 자동으로 고른다. 고른 번호를 찍어 주니
**yaml 에 옮겨 적어라.** 적어두면 자동 선택을 안 거치고 그 값으로 고정된다.

### 2.6단계 · 여러 페그 순회 (20분)

한 페그씩 따로 보는 것과 차례로 도는 것은 다르다. 조율 한 바퀴의 이동 부분을
통째로 돌려 본다. **페그를 돌리지는 않는다.** 잡았다 놓기만 한다.

```bash
python3 tools/peg_tour.py                       # 6 → 5 → 1
python3 tools/peg_tour.py --pegs 6 5 2 1        # 네 줄 전부
python3 tools/peg_tour.py --no-grip             # 잡지 않고 이동만 (첫 판은 이걸로)
python3 tools/peg_tour.py --speed 30            # 처음 가보는 경로만 느리게
```

팔 모양(sol)을 알아서 고른다. yaml 에 적혀 있으면 그걸 쓰고, 없으면 ikin 으로
8가지를 받아 위 기준으로 고른다 (`arm_pose.py`). 끝날 때 고른 값을 찍어 주니
**yaml 에 옮겨 적어라. null 로 두면 매번 달라진다.**

페그마다 한 번 확인을 받고, 그 안에서는 안 멈춘다.
처음 가보는 경로만 `--speed 30` 으로 낮춘다. 기본은 100(yaml 의 motion.vel 그대로)이다.
먼저 `--no-grip` 으로 이동만 보고, 괜찮으면 파지까지 붙인다.

기록: 각 페그의 sol, 잡힌 모양, 걸린 구간

**2026-09-19 1판(--no-grip) 통과.** 6 → 5 → 1 이 안 부딪히고 돌았다.
**2026-09-19 2판(파지 포함) 통과.** 21mm 프리셋으로 세 페그를 잡았다 놓았다.

이로써 1·2·2.5·2.6 단계가 닫혔다. 배선, 파지, 좌우 전환, 순회까지 된다.
남은 것은 **페그를 돌리는 것부터**다 (3단계).

아직 안 적은 것 — 순회가 끝날 때 찍어 준 `pegs.<번호>.sol` 값.
yaml 에 옮겨 적어야 매번 같은 팔 모양으로 간다. 지금은 전부 null 이라
로봇이 그때그때 고르고 있다.

### 대기 자세로 돌아올 때 경유지를 거쳐야 하나

**오른쪽(1·2번)에서는 거쳐야 한다.** 1번 접근점에서 대기로 직행하면
관절 보간 경로가 손끝을 헤드스톡 위로 쓸고 간다 — 경로 중간에
손끝 [352, 93, 138], [354, 85, 144] 로 페그 높이 그대로 지난다.

왼쪽(6·5번)에서는 계산상 안 걸린다. 다만 **기타 몸통 범위를 모른다.**
페그가 6번 X 342, 5번 X 306 이니 넥과 몸통은 X 380 너머로 뻗어 있을 텐데
그 부분이 검사 상자(X 280~370) 밖이다. 그래서 양쪽 다 거치게 뒀다.
몸통 범위를 실측하면 왼쪽은 직행으로 줄일 수 있다.

대기 자세는 손끝 [384, 6, 313] 으로 넥 바로 위다. 특별한 이유로 정한 자리는
아니다(2026-09-19 확인). 페그 높이에서 200mm 위라 여유는 있다.

## 3단계 · 회전 관절과 방향 (15분)

### 어느 관절이 페그를 돌리나

`motion.peg_joint: 6` 으로 가정해 뒀다(손목). 페그를 문 채 **J6 만** 돌려서
페그가 같이 도는지 본다. 팔이 딸려가거나 페그가 안 돌면 다른 관절이다.

### 조이는 방향

6번 페그를 물고 조금 돌려서 **음이 올라가는 방향**을 찾는다. 귀로도 구분된다.

그다음 1번(반대편)에서 같은 부호로 돌려 음이 어떻게 되는지 본다.

> 계산상 6·5번의 그리퍼 접근축은 BASE +Y, 1·2번은 -Y 로 정반대다.
> 그렇다면 같은 "조임"에 대해 **좌우 turn_sign 이 서로 반대**여야 한다.
> 지금 YAML 은 넷 다 `1` 이다. 확인해서 고친다.

기록: `pegs.<번호>.turn_sign` 을 +1 / -1 로

**안전**: 이 단계는 줄을 조이는 방향으로 돌아간다. 한 번에 **30도 이내**로,
음이 목표보다 너무 높아지지 않게 본다. 끊어질 수 있다.

### 2026-09-19 1차 결과 — 방향은 맞다, 토크는 안 보인다

6번 줄, 푸는 방향 30도, 2.5도씩 12회, 파지 21mm.

**회전 방향 확정.** 되돌리는(=조이는) 구간에서 음이 올라갔다.
`turn_sign: -1` 이 맞다. 나머지 셋도 같은 기하라 같은 값을 쓴다.

**관절은 명령대로 돌았다.** 30.01도 / 명령 30.00도. 각도 손실 없음.

**토크는 평평했다.** 각도를 30도까지 늘려도 저항이 안 늘었다.

```
회전 전(정지)   +0.07
회전 중         -0.30 ~ -0.41   (평균 -0.37, 흩어짐 0.11)
앞 1/3 -0.352   뒤 1/3 -0.362   기울기 +0.010
```

기울기 0.010 이 흩어짐 0.110 안에 완전히 묻힌다. **각도에 따라 커지는 성분이 없다.**

계산해 보면 그럴 만하다. 6번 줄 장력 약 70N, 페그 축 반지름 약 3mm 면
축 토크가 0.21 Nm 인데, 웜기어 감속비가 14:1 쯤이라 손잡이에서는
**0.015 Nm** 밖에 안 된다. 마찰을 넉넉히 잡아도 0.05 Nm 수준이다.
우리가 본 흩어짐이 0.11 Nm 이니 **장력 몫은 센서 잡음에 묻힌다.**

**단 정지(+0.07) → 회전 중(-0.37) 의 단차 -0.44 는 살아 있다.**
이게 기어·그리퍼 마찰이면 CLAUDE.md 3.6 의 파지 확인이 그대로 성립한다.
헛잡으면 이 단차가 없어야 한다. **`--no-grip` 으로 허공 값을 재야 갈린다.**

```bash
python3 tools/peg_turn_check.py --peg 6 --angle 30 --no-grip
```

허공 단차가 -0.44 와 비슷하면 그건 그리퍼 자체 마찰이고, 토크로는 파지를
확인할 수 없다. CLAUDE.md 3.6 을 고쳐야 한다.
허공 단차가 훨씬 작으면 임계값을 그 사이에 두면 된다.

이 회차의 원자료는 `docs/robot_data/2026-09-19_120000_turn_peg6_loosen.json`
에 있다. 도구가 로그를 남기기 전이라 화면 출력에서 손으로 옮긴 것이다.
지금은 `peg_turn_check` · `peg_tour` 가 실행할 때마다 `docs/robot_data/` 에
자동으로 떨군다. 허공 회차를 재면 저 파일과 **자동으로 견줘서** 판정까지 찍는다.

⚠️ 도구가 처음에는 "저항이 붙기 시작한 지점 2.5도" 라고 **잘못 보고했다.**
최댓값의 절반을 넘는 첫 점을 찾는 식이라, 평평한 데이터에서도 첫 점이 걸렸다.
앞 1/3 과 뒤 1/3 의 차이를 흩어짐과 견주도록 고쳤다.


## 4단계 · 기타가 밀리는지 (10분)

**여기서 밀리면 1~3단계 결과도 다 다시 해야 한다.** 먼저 확인하는 게 낫지만,
페그를 돌려봐야 알 수 있어서 3단계 뒤에 둔다.

1. 6번 페그를 잡고 그 좌표를 기록
2. 페그를 90도쯤 돌린다
3. 물러났다가 6번을 **다시 잡고** 좌표를 기록

```bash
python3 tools/peg_frame.py --repeat 6 <처음 X Y Z> <다시 X Y Z>
```

옆 방향 차이가 2mm 를 넘으면 기타가 밀린 것이다. 받침대 고정을 보강하고
2단계부터 다시 한다.

> 09-18 과 09-19 사이에 기타가 6.5mm 밀렸던 적이 있다. 사람이 옮긴 탓이었지만,
> 페그를 돌리는 힘으로도 같은 일이 생길 수 있다. 조율 도중에 밀리면
> 그 뒤에 오는 줄부터 전부 헛잡는다.

## 5단계 · 백래시 측정 (20분) — 마이크 필요

**2단계(폭·깊이)를 확정한 뒤에 해야 한다.** 파지 여유와 고무 골무의 비틀림이
그대로 헛돎에 더해지기 때문이다. 폭을 나중에 바꾸면 이 값은 무효가 된다.

```bash
python3 tools/peg_cal.py --string 6 --backlash --step 20
```

> `--step` 을 **반드시 20~30 으로 준다.** 기본값 90 은 백래시를 과대 보고하는
> 버그가 있다(첫 측정에서 이미 -5센트를 넘겨버려 역산이 안 된다).
> 모의값 40도짜리를 `--step 90` 으로 재면 90도라고 나온다.

기록: 6번·1번 백래시 각도

## 6단계 · 파지 확인 토크 임계 (20분)

페그를 제대로 물었는지는 **돌릴 때 걸리는 저항**으로 판정한다.
그 기준값을 여기서 잡는다.

1. **헛잡고 돌리기** — 페그를 빗나간 위치에서 그리퍼를 닫고 돌린다.
   `get_external_torque()` 로 회전 관절 값을 기록. 여러 번
2. **제대로 잡고 돌리기** — 같은 각도만큼 돌리며 기록. 여러 번
3. 두 분포가 갈리는 지점을 임계값으로

> 백래시를 먹기 전에는 제대로 물어도 저항이 없다. **5단계에서 잰 백래시
> 각도를 지난 뒤부터** 토크를 봐야 한다. 그래서 5단계 다음이다.

기록: 줄별 토크 임계값, 판정 시작 각도

## 7단계 · 각도-센트 상수 (30분) — 마이크 필요

서버가 "몇 센트 틀어졌으니 몇 도 돌려라"를 계산하는 데 쓰는 값이다.
지금 `tuning_logic.peg_angle()` 의 `k = 0.15` 는 확실히 틀렸다
(한 바퀴에 2옥타브라는 뜻이다. 실제는 250~350센트).

```bash
python3 tools/peg_cal.py --string 6
python3 tools/peg_cal.py --string 1 --step 45    # 고음현은 작게
```

측정 원칙 — 안 지키면 값이 튄다.

- 항상 조이는 방향으로만 돌린다
- 목표 음 ±1반음 안에서 잰다
- 손을 뗀 뒤 2~3초 기다렸다가 측정한다
- 줄을 갈고 하루 이상 지난 상태에서 잰다

기록: 줄별 센트/도 → 정동휘에게 전달

## 8단계 · 파지 확인용 WebLogic 규칙 (15분)

RG2-0 을 조건으로 걸 수 있다는 것까지 확인됐다(2026-09-19).

**그런데 더 쉬운 길이 있다** (2026-09-19 발견). Compute Box 가 Modbus 로
그리퍼 폭과 파지 감지를 그대로 내준다. WebLogic 규칙을 만들 필요가 없다.

```bash
python3 tools/gripper_status.py --watch
```

읽기만 하는 도구다. 여닫으면서 어느 레지스터가 변하는지 보면 배치가 확정된다.
지금 배치는 드라이버 코드에서 가져온 추정이다. 먼저 확인할 것 둘 —

- Compute Box(192.168.1.1)가 로봇 제어 PC 에서 보이나 (`ping 192.168.1.1`)
- 폭이 실제로 [9]번 칸에, 파지 감지가 [11]번 칸에 있나
피크는 돌리지 않아 토크로 판정할 수 없으므로 이 경로가 필요하다.

1. 웹에서 규칙 추가 — 조건에 RG2-0 의 "잡힘" 상태, 동작에 출력 하나 켜기
2. 로봇에서 `get_digital_input(그 번호)` 로 읽히는지 확인
3. 빈손일 때 0, 뭔가 물었을 때 1 이 나오는지

기록: 파지 확인 입력 번호
