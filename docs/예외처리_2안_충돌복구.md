# 충돌 복구 설계 — 로봇 예외처리 2안

2026-09-21 · 정동휘

> 아티팩트(Claude Docs)에서 저장소로 옮긴 사본이다 (2026-09-22).
> 원본은 계정에 묶여 있어 공유·인수인계가 안 되므로 이 파일이 기준본이다.

**충돌을 두 갈래로 나눠 다룬다.** 이동 중에 부딪혔으면 쥔 것을 놓고 초기 위치로
물러나 일시정지했다가 그 줄을 처음부터 다시 하고, 페그를 돌리는 중에 부딪혔으면
같은 복귀 동작을 한 뒤 **전체를 정지하고 Phase 0 부터 다시 시작한다.** 회전 중에는
`peg_state` 에 기록된 손잡이 각이 틀린 값이 되기 때문이다.

이 문서는 **2안**이다. 1안(연속 실패 중단)과 짝이다 — **1안은 지속 고장을 감지 없이
멈추는 그물이고, 2안은 충돌에서 되돌아오는 길이다.**

## 두 갈래

부딪힌 시점에 따라 끝이 다르다.

```
이동 중 충돌      쥔 것 놓기 → 초기 위치 → 일시정지 → 사람 확인 → 재개 → 그 줄 처음부터
페그 회전 중 충돌  쥔 것 놓기 → 초기 위치 → 전체 정지 → 초기화 수순 → 다시 시작하면 Phase 0 부터
```

**앞의 두 단계는 같다.** 쥔 것을 놓고 초기 위치로 물러나는 것까지는 둘이 공유한다.
갈리는 건 그다음이다 — **이어서 하느냐, 다시 시작하느냐.**

### 대상은 보호정지가 안 걸리는 수준의 충돌이다

보호정지가 걸리면 로봇이 아무것도 못 한다. 사람이 펜던트에서 해제해야 하고, 그건
이 설계의 밖이다. 여기서 다루는 건 **로봇이 멈추지 않고 그냥 밀고 가는 정도의 가벼운
충돌**이다.

### 감지는 이동 명령마다 한다

연속 감시가 아니라 **이동이 끝날 때 반환을 보는** 방식이다.
`_moved()`(`motion_primitives.py`)가 이미 그 자리에 서 있다 — 이동 함수 다섯이 전부
이걸 탄다.

## 왜 회전 중은 재개가 아니라 초기화인가

**`peg_state` 에 저장된 손잡이 각이 틀린 값이 되기 때문이다.** 이 절이 설계의
핵심이다.

`robot_controller.on_adjust` 가 **성공한 뒤에만** 각도를 누적한다.

```python
if joint == 6:
    self.pegs.add_turn(r.string_number, delta)
    self.pegs.save()
```

바로 위 주석(374~377)이 이유를 적는다 — *"돌린 만큼 손잡이도 돌아갔다. **성공한
뒤에만** 적는다 — 중간에 실패하면 얼마나 돌았는지 모르므로 누적하면 더 틀어진다."*

그 판단은 맞다. 하지만 그 결과로 **물리적으로는 돌았는데 기록은 안 돌았다고 남는다.**

### 그 상태로 이어가면 어떻게 되나

다음 `adjust_peg` 가 **틀린 각으로 진입한다.** `CLAUDE.md` 5절이 적은 그 장면이
여기서 일어난다 — *"안 맞으면 물리면서 페그를 교시 각으로 되돌려 버린다."*

더 나쁜 것은 **그게 조용히 일어난다는 점**이다. 파지는 성공하고 동작도 성공으로
보고되는데 직전에 돌린 것이 통째로 풀린다. 로봇은 모르고 서버도 모른다.

**그래서 각도를 버리고 Phase 0 를 다시 도는 게 맞다.** 다시 잡아보고 각을 확정하면
기록과 실물이 다시 맞는다.

### 이동 중 충돌은 왜 재개가 되나

**페그를 안 건드렸기 때문이다.** 손잡이 각이 그대로라 `peg_state` 를 계속 쓰면 된다.
물러나서 사람이 확인하고 다시 시작하면 그 줄을 처음부터 가면 그만이다.

즉 **갈리는 기준은 "얼마나 세게 부딪혔나" 가 아니라 "기록과 실물이 어긋나느냐" 다.**

## 선행 확인 — 무엇이 가벼운 충돌을 감지하나

**여기가 제일 불확실하다. 이게 안 풀리면 나머지가 성립하지 않는다.**

구간마다 감지 수단이 다르다.

```
순응제어 켜진 구간    힘으로 감지된다              페그 파지·후퇴
힘 제어 진입 구간     contact_force_n 으로 감지    지금 기본값이 꺼져 있다 (#53)
위치 제어 이동 구간   ???                        이번 설계가 대상으로 잡은 구간
```

**문제는 이동 구간이 전부 위치 제어라는 것이다.** PR #57 로 `speed_scale: 2.0` 이
들어가 2배 빨라진 바로 그 구간이기도 하다.

### 왜 문제인가

보호정지가 안 걸리면 **`movel` 이 `0`(성공)을 돌려줄 수 있다.** 그러면 `_moved()` 가
아무것도 못 잡고 로봇이 그냥 밀고 간다. 감지 자체가 없는 셈이다.

즉 5절의 ②③는 **감지가 된다는 전제 위에 서 있다.** 그 전제가 안 받치면 복귀 동작을
아무리 잘 만들어도 불리지 않는다.

### 확인할 것 셋

이슈 #53 에 붙이면 된다.

1. **보호정지 문턱이 얼마인가**
2. **걸린 뒤 프로그램이 움직일 수 있나** — 못 움직이면 복귀 동작 자체가 못 도는 것이다
3. **보호정지와 별개의 '충돌 감지' 기능이 두산 컨트롤러에 있나.** 있다면 민감도를
   낮춰 가벼운 충돌을 잡을 수 있는가

3번이 있으면 이 설계가 깔끔하게 성립한다. 없으면 위치 제어 구간의 가벼운 충돌은
**감지 수단이 없다는 것을 인정하고** 1안(연속 실패 중단)으로 간접 처리하는 수밖에
없다.

## 로봇이 회전 중이었는지를 어떻게 알리나

지금은 실패가 전부 `MotionError` 하나로 나가 **이동 중인지 회전 중인지 구분이 없다.**
그런데 2절에서 봤듯이 그 둘은 끝이 다르다. 방법이 둘이다.

### A. 보수적 — `adjust_peg` goal 이 실패하면 무조건 초기화

회전은 `adjust_peg` 안에서만 일어난다. 그러니 구분하지 말고 그 goal 이 실패하면 전부
초기화한다. 간단하고 안전하다 — 틀려도 **안전한 쪽으로** 틀린다.

대가는 **접근·경유 구간에서 실패해도(아직 회전 전인데) Phase 0 를 다시 도는 것**이다.
4줄을 다시 잡아보는 비용을 치른다.

### B. 정확 — 로봇이 회전을 시작했는지 알린다

`AdjustPeg.Result` 에 플래그 하나를 두거나 예외를 두 종류로 나눈다. 정확하지만
**인터페이스를 건드린다.**

### 권고 — A 로 시작하고 비용이 문제되면 B

**충돌 자체가 드물 것이라 초기화 비용을 자주 낼 일이 없다.** 드물게 일어나는 일에
인터페이스를 먼저 여는 것은 순서가 거꾸로다. 실기에서 초기화가 자주 걸리면 그때 B 로
옮긴다.

다만 B 로 옮길 때는 **이슈 #42(Phase 0 상수)와 6절②(사유 칸)를 같이 열면**
인터페이스 변경을 한 번에 끝낼 수 있다.

## 조각별 현황

네 조각이 필요하고, 그중 하나는 이미 있다.

```
① 감지        movel/movej 반환 -1 → _moved()          이미 있다
              단 3절 확인이 먼저다

② 이동 중     쥔 것 놓기 → 순응 풀기 → frames.standby   새로 만든다
              → PHASE_PAUSED + 사유                   사유 칸이 없다 (6절)

③ 회전 중     ②와 같은 복귀 동작                       공유한다
              → peg_state 폐기                        새로 만든다
              → PHASE_ERROR 또는 종료

④ 재개        그 줄 처음부터                          브리핑 B4-3 답 채우기
              재개 전 확인 항목을 화면에                피크 제자리? 기타 안 밀렸나?
```

**②와 ③가 복귀 동작을 공유한다. 한 번 만들면 둘 다 쓴다.** 갈라지는 건 복귀한 뒤의
처리뿐이다 — 일시정지하고 기다리느냐, `peg_state` 를 버리고 끝내느냐.

### 복귀 동작은 순서가 있다

무작정 `frames.standby` 로 보내면 안 된다. 세 단계를 순서대로 밟아야 한다.

1. **쥔 것 놓기** — 페그를 물고 있으면 먼저 놓는다. 그대로 팔을 움직이면 페그를 끌고 간다
2. **순응 풀기** — 순응이 켜진 채로는 위치 명령이 `-1` 이다(#31). 안 풀면 복귀 자체가 거부된다
3. **초기 위치로 이동** — `frames.standby`(`teach_points.yaml`). 이미 *"작업 시작·종료 자세"* 로 정의돼 있다

`_cleanup_register`(`motion_primitives.py`)가 이미 1·2를 같은 순서로 한다.
**거기에 3을 붙이고 바깥에서 부를 수 있게 만드는 게 이번 일의 본체다.**

## 걸리는 것 둘

### ① 사용자 pause 와 충돌 pause 가 정반대다

기획 2.7 은 pause 를 **"현재 위치 정지, 파지 유지"** 로 적는다. 이번 설계는
**"초기 위치로 이동 후 정지"** 다. 같은 단어인데 반대 동작이다.

같은 `PHASE_PAUSED` 를 쓰되 **들어온 경로가 달라야 하고 화면 문구도 달라야 한다.**
사용자가 *"내가 누른 적 없는데 왜 멈췄지"* 가 되면 안 된다. 더욱이 팔이 제자리가
아니라 **초기 위치에 가 있으니**, 그걸 모르면 "멈춰놓고 왜 움직였지" 가 된다.

둘을 가르는 것 자체는 서버 몫이다. 로봇은 실패 사유를 올리고, 서버가 "사람이 누른
pause" 와 "충돌로 인한 pause" 를 가려 화면에 다르게 싣는다.

### ② 왜 멈추었는지 실을 칸이 없다

`TuningState` 에 문자열 필드가 `job_id` 뿐이다. 지금 화면엔 빨간 '오류' 배지만 뜨고
**사유가 한 글자도 안 나온다.**

충돌 복구는 **사람이 확인하고 재개를 누르는 것이 절차의 일부**다. 뭐를 확인해야
하는지 화면이 안 알려주면 절차가 성립하지 않는다. 적어야 할 것은 적어도 셋이다 —
**어느 줄에서, 어느 단계에서(이동인가 회전인가), 뭐를 확인해야 하는지.**

인터페이스 변경이라 **이슈 #42(Phase 0 상수)와 같이 열면 된다.** 4절의 B 로 옮길
때도 같은 문이 필요하니 **셈을 한 번에 묶는 게 좋다.**

## 이 설계가 흡수하는 것

회복 조사에서 나온 구멍 둘이 여기 들어간다. 따로 고칠 필요 없이 ②③를 만들면 같이
해결된다.

### `adjust_peg` 에 정리 장치가 없다

`register_peg` 은 #52 로 `_cleanup_register` 를 갖췄다 — 놓고, 순응을 끄고,
물러난다. 그런데 **`adjust_peg` 에는 그게 없다.** 페그를 문 채 예외가 나면 아무것도
안 하고 그대로 올라간다.

**②③의 "쥔 것 놓기" 가 이걸 포함한다.** 복귀 동작의 첫 단계가 공백을 메운다.

### `_run()` 의 finally 가 복귀를 안 한다

회복 조사에서 확인한 것 — `_run()` 의 finally 는 `_running` 을 비우기만 하고
**팔 자세 복구를 안 한다.**

그것도 모르고 비워둔 게 아니다. `return_home` 의 docstring 이 직접 적는다 —
*"한계: 정상 완료 경로에만 있다. 취소·오류로 끝난 경우의 복귀는 수단이 없고 지금은
사람이 회수한다."* **알고 안 만든 것이다.**

복귀 목표도 이미 있다 — `frames.standby` 가 *"작업 시작·종료 자세"* 로 정의돼 있다.
**부를 자리만 없었다. ②③가 그 자리다.**

### 다만 조건 없는 일괄 복귀는 안 된다

`_run()` 의 except 에서 무작정 `return_home` 을 부르면 새 사고가 난다.

- **페그를 물고 있으면** 먼저 놓아야 한다. 그대로 움직이면 페그를 끌고 간다
- **순응이 안 풀렸으면** `movej` 가 `-1` 이라 복귀 명령 자체가 거부된다
- **`_holding_pick` 이 `None` 이면** 그리퍼를 건드리는 것 자체가 위험하다. 피크를
  어디에 떨어뜨릴지 모른다

그래서 5절의 **세 단계 순서가 중요하다.** 복귀는 "어디로 가느냐" 보다
**"가기 전에 무엇을 놓느냐" 가 먼저다.**

## 이 설계 밖에 남는 것

아래 셋은 충돌과 상관없이 나는 것이라 **따로 고쳐야 한다.** 복구 설계가 끝나도 남는다.

### ① `_release_pick` 에 "시도 중" 표시가 없다 (한 줄)

검사 자체는 **양쪽에 다 있다.** `_ensure_pick` 과 `_release_pick` 둘 다 들어오자마자
`_holding_pick is None` 이면 `MotionError` 를 던진다. 차이는 하나다 —

```
_ensure_pick    pick_up() 을 부르기 전에 _holding_pick = None 을 박는다
                주석도 "시도 중 — 끝나기 전엔 모른다"
_release_pick   그 표시 없이 pick_return() 을 바로 부른다
```

그래서 `pick_return()` 이 그리퍼를 열어 **피크를 놓은 뒤** 올라오다가 거기서
실패하면, `_holding_pick = False` 에 도달하지 못하고 **`True` 로 남는다.** 실제로는
놓았을 수도 있는데 "쥐고 있다" 고 기억하는 것이다.

다음 `_ensure_pick()` 이 "이미 손에 있다" 며 그냥 넘어가 **빈손으로 발현**하고
`FAIL_LOW_SIGNAL` 이 난다. 로봇이 원인인데 **화면에는 마이크 문제로 보인다.**

**고치면 "조용히 틀린다" 가 "시끄럽게 멈춘다" 로 바뀐다.** `_ensure_pick` 과 대칭이
되는 게 논리적으로도 맞다 — 반환도 집기와 똑같이 "시도 중에는 모른다" 이기 때문이다.

### ② 그리퍼에 검출이 없다

`RG2.select()` 가 `set_digital_output` 반환을 안 보고, `time.sleep` 뒤에
`self.current = name` 으로 **기록만** 한다. 폭을 읽어 확인하지 않는다. 게다가
**`RG2.current` 는 테스트만 읽는다 — 런타임에서 아무도 안 본다.**

유일한 폭 확인이 `register_peg` 의 probe 뒤 1회뿐이다. 피크·작업 파지에는 없다.

### ③ 피크 놓침은 검출 자체가 없다

`pick_up` 은 그리퍼를 닫은 뒤 폭을 안 읽는다. 비전이 없어 **떨어뜨린 피크는 되찾을
수도 없다**(`CLAUDE.md` 2절). 로봇은 계속 "쥐고 있다" 고 믿으며 빈손으로 발현하고,
서버는 재시도하며 같은 일을 반복한다.

**그래서 1안(연속 실패 중단)이 간접으로 덮는다.** 같은 줄이 계속 실패하는 걸 보고
멈추는 그물이다. 다만 **잡힐 때까지 시간을 버리므로 ①은 그 전에 고치는 게 맞다.**

## 남은 결정

셋이다. 첫째가 제일 급하다.

```
3절 확인 셋을 이슈 #53 에 붙일지              안 풀리면 ①이 성립 안 한다
4절 A 로 갈지 B 로 갈지                      A 권고
브리핑 B4-3 답을 '그 줄 처음부터' 로 채울지    사용자 의향은 그쪽
```

첫째가 무거운 이유는 **순서 때문**이다. 감지가 안 되면 복귀 동작을 아무리 잘 만들어도
**불리지 않는다.** 구현 순서를 잡을 때 이걸 먼저 두어야 한다.

둘째·셋째는 구현과 함께 가도 된다.

## 마무리 — 복귀가 필요한 상태를 안 만드는 쪽이 낫다

이 저장소에 **잘 된 예가 하나 있다.** TCP 를 못 맞췄을 때다.

`_ensure_named` 가 **움직이기 전에 멈춘다.** 되돌릴 게 없다 — 잘못된 상태로 들어가기
전에 막기 때문이다. 그래서 208mm 어긋난 진입을 원천 차단한다. 복구 코드가 한 줄도 안
필요하다.

**이 설계도 같은 원칙을 따라야 한다.** 복귀 동작을 잘 만드는 것보다 **복귀가 필요한
상태에 안 빠지는 쪽이 언제나 싸고 확실하다.** 구체적으로 셋이다 —

- **사람이 작업 전에 손잡이를 눕혀 둔다** (`CLAUDE.md` 5절 Phase 0). 사점에 빠질 일
  자체를 줄인다
- **이동 속도를 올릴 때는 그만큼 충돌 확률도 올라간다.** `speed_scale` 은 복구 비용과
  같이 저울질해야 한다 (#58)
- **감지 수단이 없는 구간은 느리게 가는 것이 유일한 안전망이다.** 3절이 안 풀리면
  그게 답이다

복구 설계는 **그래도 부딪혔을 때를 위한 것**이지, 부딪혀도 된다는 뜻이 아니다.
