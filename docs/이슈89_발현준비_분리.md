# #89 발현 준비와 마이크 시작 분리

브랜치: `fix/89-prepare-pluck`. PR #90의 녹음 샘플 보존 수정 위에서 개발했다.
코드와 자동 검증 단계이며 실물 검증은 아직 하지 않았다. PR #90에 의존하는 후속 PR로
검토한다. 실물 확인 전 이슈를 해결 완료로 닫지 않는다. RViz 연결 작업은 범위에서 제외했다.

## 바뀐 순서

기존: 마이크 ready → 피크 집기·이동·발현 → 결과 판정.
피크 집기 중 잡음 onset이 검출되면 발현 전에 측정이 끝나고, 서버가 다시 튕겼다.

변경:

1. 서버가 `/robot/prepare_pluck`를 요청한다.
2. 로봇은 필요하면 피크를 집고 대상 줄의 접촉점 위 접근점까지 간다. 아직 접촉하지 않는다.
3. 준비 성공 Result와 일회용 `preparation_id`를 서버에 돌려준다.
4. 서버가 취소·일시정지를 확인한 뒤 `/audio/measure_pitch`를 요청한다.
5. 마이크 ready 이후 `/robot/play_string`에 같은 줄과 준비 식별자를 보낸다.
6. 로봇은 준비 식별자를 소비하고 접촉·한 번 스트로크·즉시 후퇴·복귀를 수행한다.
7. 유효 측정이면 판정하고 실제 측정 실패일 때만 기존 횟수 내에서 재시도한다.

이 순서는 최초 발현·페그 조절 후·측정 재시도·최종 검증 모두에 적용된다.
피크를 다시 집을지는 서버가 아니라 로봇의 기존 `_ensure_pick()`이 판단한다.

## 구현 범위

- 새 Action `PreparePluck`: 줄 번호 → 성공 여부·설명·준비 식별자.
- `PlayString.Goal`에 `preparation_id` 추가. 다른 줄·이미 소비한 식별자는 이동 없이 실패.
- 준비 후 다른 로봇 Action이나 재준비가 끼면 이전 식별자는 무효화한다.
- 기존 단독 도구는 식별자를 비워 준비+발현 경로를 쓸 수 있다.
  새 task_manager는 빈 식별자로 진행하지 않는다.
- 로봇의 기존 `pluck_string` 경로를 나눴다. 준비는 기존 대기 자세→접근점 이동까지만 한다.
  발현에서는 앞쪽 대기 자세 경유를 생략하고 같은 접근점을 다시 명령한 뒤 접촉한다.
  발현 후 대기 자세 복귀는 유지한다.
- 기존 교시 좌표, 스트로크 방향·속도, 즉시 후퇴 거리와 오디오 판정 문턱은 바꾸지 않았다.
- 준비 중 화면은 `PHASE_PREPARE_PLUCK=13` / ‘발현 준비’로 표시한다.
  기존 상수 번호는 유지하며, 화면용 이전 측정값은 준비 시작 때 지운다.
- 준비 제한은 `prepare_timeout_sec=30.0`(실측 전 임시값)이다.
  기존 로봇 Action 정책대로 초과 후 종료 확인을 추가 대기하며, 종료가 불명하면 중단한다.
  이 시간은 onset 제한·분석 제한과 별개다. 오디오 두 제한 시간 자체는 변경하지 않았다.

## 실패·취소의 의미

- 준비 실패·거부·종료 불명·빈 식별자: 마이크/발현을 시작하지 않는다.
- 준비 중 서버 취소: 준비 동작 종료 뒤 단계 경계에서 중단하며, 마이크를 시작하지 않는다.
- 준비 단계에서 일시정지: 마이크 시작 전에 기다린다. 재개 이후 ready부터 진행한다.
- 마이크 ready 미수신: 발현하지 않고 오디오 취소를 요청한다.
- 실제 분석 실패: 재시도는 유지한다. 준비 분리는 모든 재발현을 금지하는 기능이 아니다.
- 물리적 로봇 정지 기능을 새로 구현한 것은 아니다. 진행 중 취소 요청이 즉시 팔을
  멈춘다고 해석하면 안 된다. 기존 로봇 종료 확인 정책과 사람의 안전 조치가 필요하다.

## 자동 검증

`colcon test --packages-select tunio_audio tunio_server tunio_robot`와 후속 변경 패키지
재실행 결과: 오디오 25개, 서버 79개, 로봇 329개, 총 433개 통과.

- 준비 중에는 MeasurePitch 요청이 전혀 나가지 않음.
- 준비→마이크 ready→발현 한 번 순서.
- 준비 실패/종료 불명/취소/ready 미수신 시 발현 차단.
- 실제 분석 실패 시 새 준비를 거쳐 재측정, 페그 조절 후에도 재준비.
- 준비 경로에는 접촉·스트로크 없음. 발현에는 스트로크 한 번과 후퇴 한 번.
- 로봇 Action 왕복으로 식별자 재사용·다른 줄 사용·페그 조절 후 사용 거부.
- 실제 ROS 서버와 가짜 하드웨어에서 준비 지연 0.3초, 오디오 제한 각각 0.1초인
  조건으로 호출 순서와 발현 1회·재시도 0회를 확인했다. 이 테스트의 오디오는 대역이며,
  실제 마이크 음질이나 로봇 소음을 검증한 것은 아니다.

## 적용 전 — 양쪽 PC 재빌드 필수

새 Action과 PlayString Goal 필드, TuningState 상수가 추가됐다.
구버전 실행 파일과 섞어 쓰지 말고 관제 PC·로봇 PC 모두 같은 변경본으로 빌드한다.
기존 노드를 종료한 뒤 빌드·환경 로드·재시작해야 한다.

각 PC에서:

```bash
cd /home/rokey/tunio_ws
source /opt/ros/jazzy/setup.bash
colcon build --packages-select tunio_interfaces tunio_server tunio_robot tunio_audio tunio_bringup
source install/setup.bash
ros2 interface show tunio_interfaces/action/PreparePluck
ros2 interface show tunio_interfaces/action/PlayString
```

설치된 패키지 구성이 PC마다 다르면, 해당 PC에 존재하는 소비 패키지를 선택해 빌드한다.
양쪽 PC에서 이 후속 PR의 변경을 포함한 동일 리비전을 사용한다. main에 병합되기 전에는
main에서 git pull만 해도 후속 PR의 수정이 반영되는 것은 아니다.

## 로봇 없는 수동 재확인

기존 시험 노드를 종료한 뒤 별도 도메인에서 실행한다. 77은 실제 로봇이 쓰지 않는
도메인 번호여야 한다.

```bash
cd /home/rokey/tunio_ws
source /opt/ros/jazzy/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=77
unset ROS_DISCOVERY_SERVER
ros2 launch tunio_bringup sim_robot.launch.py \
  device:=-1 port:=8080 db:=/tmp/tunio_issue89_test.db prepare_delay_sec:=22.0
```

관제에서 최대 조절 횟수를 0으로 설정하고 시작한다.
약 22초 동안 ‘발현 준비’가 보이며, **이 동안에는 튕기지 않는다.**
마이크의 ‘준비 완료 — onset 대기’ 로그가 뜬 뒤 표시된 줄을 한 번 튕긴다.
다음 측정·재시도·검증에도 준비 지연 22초가 적용된다. 시험을 빠르게 하려면
기본 `prepare_delay_sec:=0.0`으로 실행한다.

확인: 준비가 10초를 넘었어도 그 때문에 마이크가 시간 초과로 종료하지 않아야 한다.
이후 실제 소리가 기각되면 기존대로 재측정될 수 있으므로 분석 로그를 구분해 본다.

## 실물 확인 — 완료 조건

- 초기 등록 후 첫 준비에서 피크를 집고 줄 위 접근점에 멈추는지 확인.
- 준비 단계에 줄 접촉·소리가 없는지 확인.
- 마이크 ready 후 스트로크 한 번과 즉시 후퇴가 실행되는지 확인.
- 페그 조절 후에도 재집기 동안 마이크 Goal이 시작되지 않는지 확인.
- 유효 측정이면 불필요한 두 번째 PlayString 요청이 없는지 확인.
- 실제 측정 실패 시에는 정상적인 재시도가 남아 있는지 확인.

접근점에서 대기하는 구간이 새로 생겼으므로 현장 확인 없이 이슈를 해결 완료로 닫지 않는다.

## 후속 수동 시험 관찰

작업 `20260923_110911`에서 22초 준비 성공 뒤 마이크 ready가 시작되는 순서를 확인했다.
다만 6번은 돌출 부족·onset 미검출로 분석에 실패하고 정상 재측정 경로에 들어갔다.
따라서 실제 마이크 통합을 전부 성공했다고 보거나, 이후 모든 재발현이 없어졌다고 해석하지 않는다.
이번 수정은 준비 시간으로 인한 조기 종료를 분리하며, 실제 분석 실패 원인은 별도 확인 대상이다.
