# 주파수 분석 테스트 가이드

`tunio_audio` 담당자와, 마이크·주파수 측정을 직접 돌려볼 조원을 위한 문서다.
도구 사용법과 결과 읽는 법, 그리고 지금까지 실제로 발목을 잡았던 함정들을 적는다.

관련 문서는 CLAUDE.md 3.5(마이크), 4절(판정 기준), 8절(분석 방식)을 같이 볼 것.

---

## 0. 도구 세 개

전부 `tools/`에 있고 ROS와 무관하게 단독 실행된다.

- `pitch_test.py` — 마이크로 녹음해서 주파수를 재는 본 도구
- `mic_level.py` — 입력 장치별 레벨 비교. "소리 부족"이 뜰 때 원인을 가린다
- `pitch_bench.py` — 알고리즘 비교 벤치마크. 채택 근거를 대기 위한 것

**반드시 `tools/` 디렉토리에서 실행할 것.** 다른 경로에 옛 사본이 있으면 그게 실행돼서
엉뚱한 결과가 나온다. 실제로 이것 때문에 하루를 날렸다(6절 참조).

## 1. 측정 전 준비

### 1.1 OS 마이크 처리 끄기

CLAUDE.md 3.5대로 노이즈 제거·자동 음량(AGC)·에코 제거를 전부 끈다.
이 기능들은 파형과 위상을 건드리는데, YIN은 시간영역 파형으로 주기를 찾기 때문에
그 왜곡이 그대로 주기 오차가 된다. 목표 정밀도 1센트는 82.4Hz에서 0.048Hz다.

### 1.2 장치와 레벨 확인

```bash
cd ~/tunio_ws/tools
python3 pitch_test.py --list          # 장치 번호 확인
python3 mic_level.py --duration 2     # 소리를 재생해 둔 상태로
```

`mic_level.py`는 모든 입력 장치를 돌며 RMS·피크 주파수·클리핑을 찍는다.
**피크가 재생음 주파수에 서는 장치**가 실제로 소리를 받고 있는 장치다.

레벨 기준:

- **-20 ~ -12 dBFS** — 적정
- -40 이하 — 게인 부족. 시스템 입력 볼륨을 올린다
- -50 이하 — 사실상 무음. 게인이 아니라 **연결을 의심**한다

게인 조절은 PipeWire 기준:

```bash
wpctl status                      # 소스 id 확인
wpctl set-volume <id> 1.0
wpctl set-mute <id> 0
```

### 1.3 연결 문제를 알아보는 법

RMS가 -50 이하이면서 **피크가 60Hz(전원 험)에 서면** 입력 잭에 아무것도 물리지 않은 상태다.
이 패턴이 보이면 게인을 아무리 올려도 소용없다. 케이블을 확인할 것.

4극(TRRS) 이어폰을 마이크/헤드폰 분리형 잭에 꽂으면 마이크 선이 안 물린다.
그 경우 4극→3극 분배 젠더가 필요하다.

## 2. 주파수 측정 — pitch_test.py

### 2.1 기본 사용

```bash
# 기타가 얼마나 틀어졌는지 모를 때 — 목표 없이 60~500Hz 전체
python3 pitch_test.py --free --repeat 1 --debug

# 대상 줄 지정 (탐색 범위가 목표 ±2반음으로 묶인다)
python3 pitch_test.py --string 1 --repeat 1 --debug

# 본 측정 10회, 녹음 저장
python3 pitch_test.py --string 1 --repeat 10 --debug --save g1_e4
```

**`--string`을 주면 탐색 범위가 목표 ±2반음으로 제한된다.** 1번 줄이면 293.7~370.0Hz다.
기타가 그보다 많이 틀어져 있으면 측정 불가가 뜨므로, 상태를 모를 땐 `--free`로 먼저 본다.

`--save`로 저장한 WAV는 `.gitignore`의 `*.wav`에 걸려 git에 들어가지 않는다.
파일명은 톤 제너레이터 검증과 실제 기타를 구분해서 붙이는 게 좋다(예: `t_`, `g_`).

### 2.2 튕길 때 지킬 것

- **개방현으로.** 프렛을 누르지 않는다
- **다른 줄은 뮤트.** CLAUDE.md 3.5대로 한 줄씩. 1번 E4와 6번 E2는 두 옥타브 관계라 같이 울리면 공명한다
- **세기를 일정하게.** 세게 튕기면 장력이 순간 올라가 음이 높게 시작했다 떨어진다
- 로봇이 나중에 하는 것처럼 **비슷한 위치를 비슷한 각도로**

### 2.3 출력 읽는 법

```
→ f0 = 330.010 Hz [yin]   유효 프레임 72/72   RMS -16.0 dBFS   오차 +2.01 센트
```

- `[yin]` — 협대역 YIN 성공. `[fft]`나 `[yin-wide]`면 신호가 약해 후퇴한 것이다
- `유효 프레임 72/72` — 이상치로 걸러지지 않은 프레임 수. 크게 낮으면 신호 품질을 의심
- `오차 ... 센트` — **계산해서 출력만 한다. 합격/불합격 판정이 아니다**

### 2.4 "합격"의 의미를 오해하지 말 것

요약에 뜨는 합격/보통/불합격은 **반복 측정의 표준편차**만 본다.
측정 도구가 믿을 만한지를 보는 것이지, 기타가 맞았는지가 아니다.

실제로 기타가 반음 가까이(-48센트) 틀어진 상태에서도 "합격"이 떴다.
표준편차가 0.82센트로 작았기 때문이다. **재현성과 정확도는 다른 문제다.**

조율 성공 여부를 가르는 허용 센트는 아직 정해지지 않았다.
CLAUDE.md 4절에 값이 비어 있고, 11절에서 임의 하드코딩을 금지하고 있다.

## 3. 알고리즘 비교 — pitch_bench.py

### 3.1 무엇을 비교하나

- `fft` — FFT 최대 피크 + 포물선 보간 (베이스라인)
- `acf` — 자기상관 (YIN의 전신)
- `hps` — Harmonic Product Spectrum (기본파가 약할 때 유리하다고 알려짐)
- `yin` — FFT 유도 + 협대역 YIN (**현재 채택안**, `pitch_test.py`)
- `pyin` — librosa.pyin (YIN + HMM). `pip install librosa`
- `crepe` — CREPE CNN. `pip install crepe` (TensorFlow 딸려옴)

`pyin`, `crepe`는 없으면 자동으로 건너뛰고 사유를 알려준다.

**venv는 이미 `~/pitch_bench_venv`에 만들어져 있다.** 바로 쓰면 된다:

```bash
~/pitch_bench_venv/bin/python pitch_bench.py --synth --string 6
```

새로 만들어야 한다면, 순서를 지켜야 한다. 그냥 `pip install crepe`를 하면 실패한다:

```bash
python3 -m venv ~/pitch_bench_venv
~/pitch_bench_venv/bin/pip install numpy librosa "setuptools<81" wheel
~/pitch_bench_venv/bin/pip install --no-build-isolation crepe
~/pitch_bench_venv/bin/pip install tensorflow
```

- `crepe`의 setup.py가 `pkg_resources`를 쓰는데 setuptools 81부터 빠졌다.
  그래서 `setuptools<81`을 먼저 깔고 빌드 격리를 꺼야 한다
- TensorFlow가 `crepe` 의존성으로 따라오지 않으므로 따로 설치한다

**ROS 워크스페이스의 파이썬 환경에는 절대 섞지 말 것.** 벤치마크는 저장된 WAV를
오프라인 분석할 뿐이라 ROS와 완전히 분리해 돌려도 된다.

### 3.2 실행

```bash
python3 pitch_bench.py --synth --string 6        # 합성 신호 (참값 확실)
python3 pitch_bench.py --wav "g6_e2_*.wav" --string 6
python3 pitch_bench.py --robust --string 6       # 기본파 감쇠·잡음 스윕
python3 pitch_bench.py --octave --string 6       # 탐색 범위 해제 시 옥타브 오인
```

**합성과 실제를 같이 주면 마지막에 종합표가 붙는다.** 발표 자료로 쓸 형태다:

```bash
~/pitch_bench_venv/bin/python pitch_bench.py \
    --synth --wav "t3_e2_*.wav" --truth 81.9985 --string 6
```

```
  알고리즘     │      합성 오차      합성 편차 │      실제 오차      실제 편차     실패 │    시간(ms)
  ─────────┼───────────────────────┼──────────────────────────────┼──────────
  fft      │     +0.10c      0.01c │     +0.26c      0.31c   0/10 │         1
  acf      │     +0.02c      0.02c │     +0.93c      1.89c   0/10 │         3
  hps      │     +0.10c      0.01c │     +0.27c      0.31c   0/10 │         1
  yin      │     -0.11c      0.11c │     +0.06c      0.82c   0/10 │        47
  pyin     │     -2.70c      0.00c │     -1.40c      0.00c   0/10 │        13
  crepe    │     +5.64c      0.95c │     +7.06c      0.84c   6/10 │      3078
```

이 표 하나가 4.3의 핵심을 다 담는다. **`acf`는 합성에서 1위(+0.02c)지만 실제에서 하위(+0.93c)로
내려가고, `yin`은 합성에서 중간이지만 실제에서 1위(+0.06c)로 올라온다.**
한쪽만 보면 결론이 뒤집히는 이유이자, 두 신호를 반드시 같이 봐야 하는 이유다.

`--all`은 강건성·옥타브까지 포함하지만, 종합표를 보려면 `--synth`와 `--wav`가
둘 다 필요하다.

### 3.3 신호 세 종류와 각각이 답하는 질문

- **합성 신호** — 참값을 아는 유일한 조건. **절대 정확도**는 여기서만 말할 수 있다
- **톤 녹음** — 마이크 경로까지 포함. 배음 역산으로 준참값을 확정할 수 있다
- **실제 기타 녹음** — 참값은 모른다. **재현성(표준편차)만** 유효하다

`--truth`로 참값을 주지 않으면 절대 오차는 계산하지 않는다.
실제 기타 녹음에서 "평균 오차"를 보고하면 안 되는 이유다.

### 3.4 시험 설계의 함정 두 가지

둘 다 실제로 밟아서 잘못된 결론을 냈던 것들이다.

**기본파 감쇠 스윕에는 반드시 잡음을 같이 넣어야 한다.**
잡음이 없으면 탐색 범위 안에 기본파밖에 없어서, 아무리 깎아도 여전히 최대 피크다.
감쇠가 무의미해지고 모든 알고리즘이 똑같이 완벽해 보인다.
현재 구현은 SNR 30dB를 고정으로 깔고 감쇠를 스윕한다.

**합성 신호의 f0를 목표 주파수와 같게 두면 안 된다.**
`pyin`·`crepe`처럼 주파수를 격자로 양자화하는 알고리즘은 목표가 격자에 정확히
떨어지면 공짜로 만점을 받는다. 처음 시험에서 `pyin`이 오차 0.00센트, 표준편차 0.00으로
나왔던 것이 이 때문이었다. `--detune`으로 f0를 목표에서 벗어나게 한다(기본 -37.3센트).
실제 기타는 언제나 목표에서 벗어나 있으므로 이쪽이 현실적이다.

## 4. 지금까지의 결과 (2026-09-18, 잠정)

### 4.1 마이크·알고리즘 검증 — 통과

톤 제너레이터 기준, 현재 채택안(`yin`)의 성적:

- 330Hz(1번 줄 대역) — 10회 표준편차 **0.02센트**, 절대 오차 0.05센트
- 82Hz(6번 줄 대역) — 10회 표준편차 **0.82센트**, 절대 오차 0.06센트

82Hz 시험은 조건이 나빴다. 핸드폰 스피커가 저음을 못 내면서 클리핑돼
**기본파가 3배음보다 20dB 작은** 상태였는데, 그 조건에서도 3배음에 속지 않았다.
탐색 범위를 ±2반음으로 묶은 CLAUDE.md 3.3 설계가 실전에서 확인된 셈이다.

### 4.2 실제 기타 — 1번 줄 통과, 6번 줄은 여유 없음

#### 넥 장력 상호작용 — 한 줄을 풀면 다른 줄이 30센트 움직인다

6번 줄만 F#2(+217센트)에서 E2로 풀었는데, **손대지 않은 1번 줄이 함께 움직였다.**

- 6번 조율 전 — 1번 줄 320.577 Hz (-48.20센트)
- 6번 조율 후 — 1번 줄 326.261 Hz (-17.77센트)
- **변화 +30.4센트**

넥에 걸리는 총 장력이 줄면서 넥이 펴지고 1번 줄이 조여진 것이다.
CLAUDE.md 5절이 최종 검증 패스를 넣은 근거가 실측으로 확인됐고,
30센트는 어떤 허용치를 잡든 훨씬 큰 값이다.
**조율 순서를 한 바퀴 돌고 나면 먼저 맞춘 줄은 확실히 틀어져 있다.**
검증 패스는 선택이 아니라 필수다.

#### 타현 방식이 배음 구조를 바꾼다

같은 1번 줄을 같은 사람이 쳤는데 배음 구조가 크게 달랐다.

- `t3_e4` — 1f=0, 2f=-5.8, 3f=-2.6, **4f=-29.0, 5f=-23.6** dB (고차 배음 거의 없음)
- `g1_e4` — 1f=0, 2f=-6.6, 3f=-3.4, **4f=-1.1, 5f=+0.7** dB (5배음이 기본파보다 강함)

브릿지에 가까이 칠수록 고차 배음이 강조된다.
**로봇 타현 위치가 정해지면 배음 프로필을 다시 재고
`pitch_bench.py`의 `HARMONICS`를 갱신해야 한다.**
다행히 측정 자체는 영향이 적었다 — 오히려 표준편차가 0.82에서 0.59센트로 좋아졌다.

#### 감긴 줄과 민 줄의 비조화성 차이

- 6번 E2 (감긴 줄) — **B = 3.33e-4**, 통상값(1e-5~1e-4)보다 크다
- 1번 E4 (민 줄) — **B ≈ 0** (피팅값 -1.0e-5, 음수는 비물리적이므로 측정 하한)

이 때문에 6번 줄에서는 배음 역산 f0가 실제보다 9센트 높게 나왔고,
1번 줄에서는 같은 방법이 1센트 이내로 맞았다.
**"왜 저음현이 어려운가"의 물리적 근거이기도 하다.**

#### 1번 줄 반복 측정에서 관찰된 것

10회 측정 표준편차 **0.82센트**(`t3_e4` 기준). 실제 악기에서 이 정도면 좋다.

**줄이 계속 풀린다.** 10회 튕기는 사이 앞 5회 평균 320.703Hz에서
뒤 5회 평균 320.452Hz로, **-1.36센트** 이동했다. 측정 오차가 아니라 실제 이완이다.
조율 루프 설계에 영향을 준다 — 맞춰놓아도 몇 번 더 튕기는 사이 벗어난다.
CLAUDE.md 5절의 최종 검증 패스는 넥 장력 상호작용을 근거로 넣은 것인데,
**줄 자체 이완이라는 원인이 하나 더 확인됐다.**

**`--skip`을 늘려도 개선되지 않는다.** 0.0 / 0.3 / 0.5 / 0.8 / 1.0초를 전부 시험했으나
표준편차가 0.78~0.91센트로 차이가 없었다. 어택 직후 음정 하강은 이 녹음에서 문제가 아니었다.
기본값 0.3을 그대로 두면 된다.

### 4.3 알고리즘 비교 — 채택안 유지가 타당하다

6개 전부 비교했다. 6번 줄 **실제 기타** 녹음은 아직 없다(아래는 톤 녹음).

#### 참값을 아는 저음 녹음이 가장 결정적이다

82Hz 톤 녹음 10개. 배음 역산으로 참값을 81.9985Hz까지 확정해두었으므로
**절대 정확도와 재현성을 동시에** 볼 수 있는 유일한 자료다.
기본파가 3배음보다 20dB 약한, 6번 줄과 비슷한 조건이기도 하다.

평균 오차 / 표준편차 / 소요시간 순:

- `yin` — **+0.06센트** / 0.82c / 54ms  ← 현재 채택안, 절대 정확도 1위
- `fft` — +0.26센트 / 0.31c / 1.7ms
- `hps` — +0.27센트 / 0.31c / 1.2ms
- `acf` — +0.93센트 / 1.89c / 5.9ms
- `pyin` — -1.40센트 / 0.00c / 74ms
- `crepe` — +7.06센트 / 0.84c / 3182ms, **10회 중 6회 실패**

#### 6번 줄 실제 기타 — 채택안이 1위, `acf`는 탈락

`g6_e2_*.wav` 10개. 참값을 모르므로 재현성만 유효하다.

- `yin` — **2.15센트** / 41ms  ← 현재 채택안
- `crepe` — 1.82센트 / 2945ms (오차는 아래 참조)
- `acf` — 2.45센트 / 3.4ms
- `fft` — 2.55센트 / 1.0ms
- `hps` — 2.58센트 / 1.2ms
- `pyin` — 0.00센트(격자 스냅) / 14ms, 1회 실패

재현성만 보면 비슷해 보이지만 **추정값 자체가 두 무리로 갈린다.**

- `fft` 81.979 / `hps` 81.983 / `yin` 81.937 Hz
- `acf` **82.829** / `pyin` 82.407 / `crepe` 82.408 Hz

기본파 피크는 81.979Hz에 뚜렷하게 서 있다. 즉 뒤쪽 세 개는 계통적으로 높다.
`acf`는 **+17.8센트**나 벗어났다. 비조화성이 큰 실제 저음현에서는
파형이 엄밀히 주기적이지 않아 자기상관이 주기를 짧게 잡기 때문이다.
1번 줄에서 `acf`가 가장 좋아 보였던 것은 그 줄의 비조화성이 작았기 때문이고,
**6번 줄에서는 쓸 수 없다.**

#### 1번 줄 실제 기타 — 채택안이 1등이 아니다

`g1_e4_*.wav` 10개. 재현성 / 추정값:

- `fft` — **0.28센트** / 326.208 Hz
- `hps` — **0.28센트** / 326.206 Hz
- `acf` — 0.33센트 / 326.289 Hz
- `yin` — 0.62센트 / 326.264 Hz  ← 현재 채택안, 4위
- `crepe` — 0.82센트 / 326.464 Hz
- `pyin` — 0.00센트(격자) / 325.842 Hz

`pyin`(-1.94c)과 `crepe`(+1.36c)를 빼면 추정값이 0.5센트 안에 모인다.
이 줄은 비조화성이 0에 가까워 `acf`도 +0.43센트로 멀쩡하다.
6번 줄에서 +17.8센트 틀렸던 것과 정반대다.

**고음에서는 더 단순한 `fft`·`hps`가 채택안보다 안정적이다.**

#### 그래서 채택 근거는 이렇게 쓴다

두 줄을 같이 놓으면 "우리 것이 제일 좋다"는 성립하지 않는다.

- 1번 줄 — `fft`/`hps` 0.28c, `yin` 0.62c로 뒤짐
- 6번 줄 — `yin` 2.15c, `fft` 2.55c, `hps` 2.58c로 앞섬. `acf`는 +17.8c 계통오차로 탈락

> `yin`은 모든 조건에서 1등이 아니다. 고음에서는 더 단순한 `fft`나 `hps`가
> 오히려 안정적이다. 그러나 기본파가 3배음보다 10dB 약하고 비조화성이 큰
> 저음현(6번 E2)에서 정확도와 재현성을 동시에 유지한 것은 `yin`뿐이었다.
> 대상 줄에 6번이 포함되는 이상 `yin`을 채택한다.

줄마다 다른 알고리즘을 쓰는 선택지도 있다(고음 `fft` 1ms, 저음 `yin` 22ms).
검토했으나 이득이 0.3센트 수준이라 복잡도에 값하지 않는다고 판단했다.

#### 6번 줄은 1센트를 못 맞춘다

가장 좋은 `yin`도 표준편차 **2.15센트**다. 1번 줄이 0.82센트였던 것과 대조된다.
기본파가 3배음보다 10dB 약해 신호 자체가 불리하다.

**허용 센트를 1~2센트로 잡으면 6번 줄은 물리적으로 통과할 수 없다.**
측정 노이즈 2.15센트에 4.2에서 관찰한 줄 이완까지 겹치므로,
±3~5센트 쪽이 현실적이다. 최종 결정은 페그 제어 분해능이 나와야 한다.

#### 고음에서는 순위가 달라진다

실제 기타 1번 줄 녹음 10개(참값 미상이라 재현성만 유효):

- `acf` 0.63c, `yin` 0.82c, `pyin` 0.00c, `crepe` 1.02c, `fft` 1.52c, `hps` 66.24c

`acf`가 고음에서는 `yin`보다 재현성이 좋지만, **저음에서는 1.89c로 무너진다.**
대상 줄에 6번 E2가 포함되는 이상 저음 성능이 선택을 좌우한다.

#### 1번 줄 조건 합성 — 위쪽 넷은 사실상 동점

1번 줄 배음 프로필은 `t3_e4_1.wav`에서 뽑은 **실측값**이라 6번 줄보다 신뢰도가 높다.

반복 10회(SNR 30dB) 기준 평균 오차:

- `acf` +0.01c, `fft` +0.03c, `hps` +0.03c, `yin` +0.04c — 넷 다 **0.05센트 이내**
- `crepe` +2.43c, `pyin` -2.70c

**고음에서 깨끗한 신호면 어느 것을 써도 차이가 없다.** 선택은 저음에서 갈린다.

#### 합성 신호 결과를 실제 신호에 일반화하지 말 것

6번 줄 조건의 기본파 감쇠 스윕에서는 `yin`이 가장 약했다
(-20dB에서 0.85센트, **-30dB에서 7.69, -40dB에서 11.18**로 무너짐).
반면 `acf`는 -40dB까지 0.03센트를 유지했다.

그런데 **실제 저음 녹음에서는 정반대로 `yin`이 1위, `acf`가 하위였다.**

같은 시험을 1번 줄 조건으로 돌리면 `yin`은 -40dB에서도 **0.72센트**로 버틴다.
즉 `yin`의 취약성은 알고리즘 자체의 성질이라기보다
**배음 프로필과 잡음 레벨의 조합**에서 나온다.
그런데 그 6번 줄 프로필은 아직 추정값이다(4.3 끝 참조).

**합성은 참값을 아는 대신 현실을 덜 담는다. 두 결과가 갈릴 때는 실제 녹음을 따른다.**

`hps`가 이를 가장 잘 보여준다. 1번 줄 합성에서는 +0.03센트로 완벽하고
6번 줄 실제 녹음에서도 +0.27센트로 멀쩡한데, **1번 줄 실제 녹음에서만 66센트로 터진다.**
합성으로는 재현되지 않는 실패다.

#### pyin의 표준편차 0.00은 장점이 아니다

`pyin`은 주파수를 격자(기본 10센트)로 양자화해 출력한다.
그래서 항상 같은 값이 나와 표준편차가 0.00c로 찍히지만,
정확도는 -1.40 ~ -2.70센트로 치우쳐 있다. **재현성이 정확도를 뜻하지 않는 전형적인 예다.**

더 문제는 미세 변화를 놓친다는 점이다. 4.2에서 관찰한 "10회 튕기는 사이 -1.36센트 이완"
같은 변화를 `pyin`은 전부 같은 격자로 뭉개서 보지 못한다. 조율 루프에는 치명적이다.

#### crepe는 성능이 아니라 용도가 다르다

저음 녹음에서 **10회 중 6회 실패**, 성공한 경우도 +7.06센트, 회당 3.2초가 걸렸다.
CLAUDE.md 4절의 "측정 응답 목표 2초"를 혼자서 초과한다.

이는 모델이 나빠서가 아니다. CREPE 논문의 지표는 50센트 이내 정확도(RPA)이고
출력이 20센트 빈의 가중평균이며, 16kHz로 리샘플링해 동작한다.
학습 데이터도 주로 음성 대역이라 82Hz는 취약하다.
**1센트급 정밀도를 겨냥한 모델이 아니다.**

#### 옥타브 오인은 알고리즘이 아니라 배음 구조가 만든다

탐색 범위를 60~500Hz로 풀었을 때(12조건), 두 줄의 결과가 정반대다.

- **6번 줄 조건** — `fft`/`yin`이 **0/12**, 전부 2배음으로 감.
  `acf`/`hps`/`pyin`/`crepe`는 12/12 정답
- **1번 줄 조건** — **여섯 개 전부 12/12 정답**

같은 알고리즘인데 줄에 따라 전멸과 만점이 갈린다. 원인은 배음 프로필이다.
1번 줄은 기본파가 가장 강해(2배음이 -2.4dB) FFT 최대 피크가 기본파에 선다.
저음현은 2배음이 기본파보다 강해서(프로필상 +12dB) 최대 피크가 2배음으로 간다.
`yin`은 FFT로 위치를 잡고 시작하므로 FFT가 틀리면 같이 틀린다.

즉 **옥타브 오인은 알고리즘 우열이 아니라 저음현 고유의 위험**이고,
CLAUDE.md 3.3이 탐색 범위를 묶은 이유가 정확히 이것이다.
운용 시에는 ±2반음으로 묶으므로 이 상황 자체가 생기지 않는다.

#### 합성 배음 프로필의 신뢰도가 두 줄이 다르다

`pitch_bench.py`의 `HARMONICS`는 합성 신호의 배음 구조를 정한다.

- `HARMONICS[1]` — **실측값.** `t3_e4_1.wav`에서 뽑았다
  (0.0 / -2.4 / -0.3 / -25.8 / -20.1 / -22.4 dB)
- `HARMONICS[6]` — **실측값.** `g6_e2_*.wav` 10개 평균
  (0.0 / +6.5 / +10.3 / -0.9 / +3.2 / -4.5 dB)

둘 다 실측으로 교체되어 더 이상 가정에 기대지 않는다.
비조화성 계수도 `INHARM`에 실측값을 넣었다 (6번 줄 B=3.33e-4, 1번 줄은 추정 1e-4).

#### 남은 확인 사항

- `hps`가 실제 기타 1번 줄에서만 66센트로 실패한 원인.
  6번 줄 실제 녹음과 1번 줄 합성에서는 멀쩡해서 비조화성 탓으로 추정되나
  구현 검증이 필요하다
- `yin`이 6번 줄 조건 기본파 -30dB 이하에서 무너지는 것은 사실이다.
  실제 6번 줄이 그 영역에 들어가는지 확인해야 한다

## 5. 발표·보고서용으로 정리할 때

- **절대 정확도는 합성 신호에서만** 주장할 수 있다. 실제 녹음은 참값을 모른다
- **재현성과 정확도를 구분해서** 쓴다. `pitch_test.py`의 "합격"은 재현성만 본 것이다
- 모든 알고리즘이 깨끗한 신호에서는 비슷하게 나온다.
  **어느 지점에서 무너지는지**가 진짜 비교 결과다
- `crepe`가 정확도에서 밀린다면 그건 성능 문제가 아니라 **용도 차이**다.
  CREPE 논문의 지표는 50센트 이내 정확도(RPA)이고 출력이 20센트 빈의 가중평균이라,
  애초에 1센트급 정밀도를 겨냥한 모델이 아니다. 16kHz로 리샘플링해 동작하기도 한다
- 처리 시간은 CLAUDE.md 4절의 "측정 응답 목표 2초"와 비교해서 쓴다

## 6. 하루를 날린 함정들 — 같은 실수 반복 금지

### 6.1 옛 사본 실행

홈 디렉토리에 `pitch_test.py` 구버전이 있었고, 거기서 실행하는 바람에
대역통과와 2단계 추정이 빠진 코드가 돌았다. 같은 녹음인데 표준편차가
**7.39센트 대 0.32센트**로 갈렸다.

증상: 출력에 `[yin]` 같은 방법 표시가 없다.

확인:

```bash
cd ~/tunio_ws/tools
grep -c "def fft_peak" pitch_test.py    # 1이면 정상, 0이면 구버전
```

### 6.2 마이크가 연결되지 않은 채로 측정

USB 사운드카드는 꽂혀 있는데 거기에 마이크가 안 물린 상태로 이틀을 측정했다.
RMS -54dBFS에 60Hz 험만 잡히는 상태였다. `mic_level.py`로 장치를 나란히 비교하면 바로 보인다.

### 6.3 샘플레이트 불일치

`pitch_test.py`는 `SR = 44100` 고정이다.
SOF 내장 코덱과 USB 오디오는 대개 **48kHz 전용**이라 `--device`로 하드웨어 장치를
직접 지정하면 "Invalid sample rate"로 실패한다.
PipeWire(`default`)를 거치면 리샘플링돼서 열린다.

**`tunio_audio` 노드에서 장치를 직접 열 때 이 문제를 다시 만난다.**
`--sr` 옵션이나 장치 기본 샘플레이트 자동 감지가 필요하다.

### 6.4 톤 제너레이터의 주파수를 반올림값으로 설정

82.4069Hz 대신 82Hz를, 329.6276Hz 대신 330Hz를 재생하면
측정이 정확해도 -8.6센트, +1.95센트가 정답이 된다.
이걸 알고리즘 오차로 오해하기 쉽다. **목표 주파수를 그대로 입력하는 게 안전하다.**

참값이 의심되면 배음에서 역산한다. 3·5·7·9배음을 차수로 나누면
기본파보다 훨씬 정밀하게 나온다. 실제로 이 방법으로 재생음이 81.9985Hz임을
표준편차 1.58mHz로 확정했다.

### 6.5 톤 제너레이터로 저음 시험의 한계

핸드폰·노트북 스피커는 82Hz를 제대로 못 낸다. 저역 한계가 보통 300~500Hz다.
82.41Hz를 재생해도 기본파는 거의 안 나오고 심하게 왜곡된 신호(홀수 배음만 남은
사각파 비슷한 것)가 나온다. 결과가 나쁘면 **마이크를 의심하기 전에 재생 쪽을 확인할 것.**

## 7. 남은 작업

- 6번 줄 실제 기타 녹음 10회 → 저음현에서의 재현성 확인
- 6번 줄 실측 배음 프로필을 `pitch_bench.py`의 `HARMONICS[6]`에 반영
  (현재는 추정값이다)
- 허용 센트 확정 — 로봇 페그 제어의 각도 분해능(1도당 몇 센트)이 나와야 정할 수 있다
- 안정화 판정 구현 (CLAUDE.md 8절) — 짧게 여러 번 측정해 값이 모이면 반환
- `pitch.py` 이식 — `SR` 하드코딩 해소 포함
