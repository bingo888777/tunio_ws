# 페그 실측 가이드

작성 2026-09-19
대상: 실측을 직접 하는 사람. 로봇 담당과 서버 담당이 같이 본다.

---

## 0. 왜 이게 없으면 아무것도 안 되나

`task_manager` 는 "측정값이 목표보다 몇 센트 낮다" → "페그를 몇 도 돌려라"를 계산한다.
그 변환에 **줄마다 다른 상수 네 개**가 필요하다. 지금은 전부 `0.0` 이고
`measured: false` 라, **조절이 필요해지는 순간 `PHASE_ERROR` 로 멈춘다.**

일부러 그렇게 만들었다. 지어낸 각도로 페그를 돌리면 줄이 끊어지거나 페그가 상한다.
측정과 판정까지는 실측 없이도 정상 동작한다.

---

## 1. 채울 파일

**`src/tunio_server/config/peg_calibration.yaml`** 하나다.

```yaml
/task_manager:
  ros__parameters:
    peg_calibration:
      measured: true              # 네 값을 다 채운 뒤에 true 로 바꾼다
      measured_at: '2026-09-22'   # 실측 날짜. 줄을 갈면 다시 재야 한다

      s6:   # 6번 E2 82.4069Hz
        cents_per_deg: 0.152
        min_effective_deg: 2.0
        max_angle_deg: 360.0
        backlash_release_cents: 28.0
      s5:   # 5번 A2 110.0000Hz
        ...
      s2:   # 2번 B3 246.9417Hz
        ...
      s1:   # 1번 E4 329.6276Hz
        ...
```

`s6` `s5` `s2` `s1` 네 줄만 있으면 된다. 4·3번은 조율 대상이 아니다.

**`measured: true` 로 올리려면 줄당 네 값이 모두 0보다 커야 한다.**
하나라도 0이면 로더가 거부한다. "true 로 해뒀는데 값은 0" 인 상태를 막기 위한 것이다.

## 2. 값 네 개가 각각 무엇인가

### `cents_per_deg` — 페그 1도당 음정이 몇 센트 변하는가

제일 중요한 값이다. 회전량이 이걸로 나온다.

```
돌릴 각도 = |센트 오차| / cents_per_deg
```

**줄마다 다르다.** 같은 페그라도 줄 장력과 굵기가 달라서, 6번 E2와 1번 E4를 한 값으로
묶으면 한쪽은 반드시 틀린다. 대체로 **고음현일수록 값이 크다**(조금만 돌려도 많이 변한다).

### `min_effective_deg` — 이보다 작게 돌리면 실제로 안 움직이는 각도

기어 유격과 파지 미끄러짐 때문에 아주 작은 각도는 먹히지 않는다.

이 값이 없으면 **오차가 작을 때 0에 가까운 각도를 반복해서 보내며 조절 횟수만 소진한다.**
화면에는 계속 돌리는 것처럼 보이는데 음은 그대로인 상태가 된다.

이 값에는 **숨은 의미가 하나 더 있다.** `min_effective_deg × cents_per_deg` 보다 작은
허용 센트는 **원리상 수렴하지 않는다.** 한 번 돌리면 그보다 크게 움직이기 때문이다.
실측이 끝나면 이 값이 허용 센트의 사실상 하한이 된다.

### `max_angle_deg` — 한 번에 돌릴 수 있는 각도 상한

안전장치다. 오차가 크게 나왔을 때 계산값이 그대로 나가면 페그를 과하게 돌린다.
넘으면 잘라서 보내고 **다음 조절 회차에서 이어서 맞춘다.**

손목 관절의 가동 범위와 페그 파지 자세에서 한 번에 돌릴 수 있는 한계로 정한다.

### `backlash_release_cents` — 목표보다 높을 때 얼마나 풀었다 조일지

**최종 접근은 항상 조이는 방향이어야 한다** (CLAUDE.md 3.2). 조였다 풀었다 하면 같은
각도라도 결과가 달라진다.

음이 목표보다 높으면 바로 풀 수 없다. **목표 아래로 충분히 풀었다가 조여 올린다.**
그 "충분히"가 몇 센트인지가 이 값이다. **측정한 백래시 양보다 넉넉해야 한다.**

## 3. 측정 방법

`tools/peg_cal.py` 가 주파수 측정·센트 환산·회귀·편차 점검을 자동으로 한다.
**사람은 페그를 돌리고 몇 도 돌렸는지 입력하기만 하면 된다.**

```bash
source /opt/ros/jazzy/setup.bash && source install/setup.bash

python3 tools/peg_cal.py --string 6              # cents_per_deg
python3 tools/peg_cal.py --string 1 --step 45    # 고음현은 작게 돌린다
python3 tools/peg_cal.py --string 6 --backlash   # backlash_release_cents
python3 tools/peg_cal.py --string 6 --min-angle  # min_effective_deg
python3 tools/peg_cal.py --string 6 --simulate 0.2   # 기타 없이 흐름만 확인
```

`max_angle_deg` 는 도구가 재지 않는다. **로봇 담당이 가동 범위를 보고 정한다.**

### 지키지 않으면 값이 튀는 것들

- **항상 조이는 방향으로만 돌린다.** 방향을 바꾸면 백래시로 헛돈다
- **목표 음 ±1반음 안에서 잰다.** 느슨한 상태에서는 같은 각도라도 덜 변한다
- **손을 뗀 뒤 2~3초 기다렸다가 측정한다**
- **줄을 갈고 하루 이상 지난 상태에서 잰다.** 새 줄은 계속 늘어난다

### 순서가 중요하다

**파지 폭을 먼저 확정하고 백래시를 잰다.**

페그는 여유를 준 폭으로 물어야 한다. 꽉 물면 손목 회전축과 페그 축이 조금만 어긋나도
옆힘이 걸려 많이 못 돌린다. 그런데 **그 여유가 그대로 백래시가 된다.**
폭을 바꾸면 백래시도 바뀌므로, 폭을 정한 뒤에 재야 두 번 일하지 않는다 (CLAUDE.md 3.6).

## 4. 채운 뒤 확인

```bash
colcon build --packages-select tunio_server && source install/setup.bash
ros2 launch tunio_bringup real_all.launch.py          # dry_run 기본 true — 안 움직인다
```

기동 로그에 이렇게 뜨면 제대로 읽힌 것이다.

```
[task_manager]: 페그 캘리브레이션 로드 (실측일 2026-09-22)
```

`실측일 SIMULATION` 으로 뜨면 시뮬레이션 파일을 읽은 것이니 인수를 확인한다.
값이 잘못됐으면 기동할 때 사유와 함께 거부한다.

## 5. 지금 값이 없어도 할 수 있는 것

실측 전에도 두 단계까지는 검증된다.

**`sim_all`** — 로봇도 마이크도 없이 화면과 서버 흐름을 본다.
지어낸 상수로 수렴하는 것이라 **조율 성능의 근거가 되지 않는다.**

**`sim_robot`** — 마이크만 진짜로 쓴다. 사람이 직접 줄을 튕겨 **측정이 맞는지** 본다.
페그는 사람이 감으로 돌린다. 이 단계의 목적은 페그 정확도가 아니라 측정 검증이다.

두 launch 모두 `peg_calibration.sim.yaml` 을 쓴다. **지어낸 값이라 실제 로봇에 쓰면 안 된다.**
`real_all` 은 그 파일을 지정하지 않으므로 실측 전에는 조절 단계에서 멈춘다.

---

## 6. 값이 바뀌는 때

- **줄을 갈았을 때** — 새 줄은 장력이 안정될 때까지 계속 늘어난다. 하루 이상 두고 다시 잰다
- **파지 폭이나 힘을 바꿨을 때** — 백래시가 따라 바뀐다
- **기타를 바꿨을 때** — 전부 다시 잰다

`measured_at` 에 날짜를 남기는 이유가 이것이다. 값이 언제 것인지 모르면 신뢰할 수 없다.
