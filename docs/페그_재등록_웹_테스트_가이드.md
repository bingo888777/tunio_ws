# 페그 재등록 웹 테스트 가이드

작성: 2026-09-23. 대상 브랜치 `feat/web-peg-registration-alert` (#100 병합 이후).
웹 재등록 버튼과 미등록 오류 안내를 포함한다. 문서 전용 PR #99만으로는 버튼이 추가되지 않는다.

## 0. 무엇을 확인하나

- 버튼 → HTTP → `/tuning/reregister_pegs` 서비스 연결.
- 접수와 완료가 구분되는지, 등록·복귀 후 완료 안내가 나오는지.
- 재등록만 했을 때 발현·마이크 측정·조율·DB 저장이 없는지.
- 조율/일시정지 중 재등록이 차단되는지.
- 연결 실패나 중간 상태 누락을 완료라고 표시하지 않는지.

이번 웹은 기존 관제 web_node다. 별도 FastAPI 앱(8001)은 사용하지 않는다.
로봇 없는 시험은 실제 페그 각도·등록 JSON·J6·접촉 경로를 검증하지 않는다.

## 1. 기존 실행 종료 / 빌드

기존 station, sim_all, sim_robot, 별도 fake_hardware 실행 터미널에서 Ctrl+C로 종료한다.
새 터미널에서 아래를 실행한다. 다른 브랜치의 미커밋 작업은 보존하고, 이 PR 브랜치가 체크아웃된 폴더에서 실행한다.
현재 PC의 PR 작업 폴더는 `/tmp/tunio-web-registration-pr`이다. 아래 `cd`는 이 폴더를 기준으로 적었다. 다른 PC나 병합 후 기본 작업 폴더에서 실행할 때는 실제 저장소 경로로 바꾼다.

```bash
cd /tmp/tunio-web-registration-pr
git branch --show-current
source /opt/ros/jazzy/setup.bash
colcon build --packages-select tunio_interfaces tunio_server tunio_robot tunio_audio tunio_bringup
source install/setup.bash
ros2 interface show tunio_interfaces/action/RegisterPeg
ros2 interface show tunio_interfaces/msg/TuningState
```

확인:

- 브랜치 출력: `feat/web-peg-registration-alert`.
- 빌드 성공.
- TuningState에 `string error_message`가 존재. 모든 관련 노드를 재시작한다.
- RegisterPeg Goal에 `uint8 string_number`와 `bool force`가 존재.

## 2. 모든 시험 터미널의 공통 환경

새 터미널마다 아래를 실행한다. 177은 실물 로봇이 사용하지 않는 도메인 번호여야 한다.

```bash
cd /tmp/tunio-web-registration-pr
source /opt/ros/jazzy/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=177
unset ROS_DISCOVERY_SERVER ROS_SUPER_CLIENT
```

이후 실제 통합으로 돌아갈 때는 새 터미널에서 기존 도메인·Discovery 설정을 다시 적용한다.
아래 시험에는 실제 robot_controller나 두산 드라이버를 띄우지 않는다.

## 3. 터미널 A — 관제 서버만 시작

2절 공통 환경 설정 후:

```bash
ros2 launch tunio_server server.launch.py \
  port:=8090 open_browser:=false \
  db:=/tmp/tunio_web_reregister_test.db \
  2>&1 | tee "/tmp/tunio_web_reregister_server_$(date +%Y%m%d_%H%M%S).log"
```

브라우저에서 **http://localhost:8090**을 연다.

- ‘페그 재등록’ 버튼이 보여야 한다.
- 상태를 받기 전에는 버튼이 비활성이다. 연결되고 대기 상태를 받으면 활성화된다.
- 버튼이 없으면 빌드·source·노드 재시작 여부를 확인하고 Ctrl+Shift+R로 새로고침한다.
- 기존 8080/FastAPI 8001 페이지와 혼동하지 않는다.

### 먼저 거부 응답 확인

아직 로봇 대역을 켜지 않은 상태에서 페그 재등록을 한 번 누른다.
서비스의 준비 검사 시간을 기다린다.

기대 결과:

- 노드 준비 안 됨 또는 필요한 robot 서버를 찾을 수 없다는 사유가 표시된다.
- 재등록 완료로 표시되지 않는다.
- 재등록/시작 버튼이 영구적으로 잠기지 않는다.

## 4. 터미널 B — 로봇 응답만 가짜로 제공

새 터미널에서 2절 공통 환경 설정 후:

```bash
ros2 run tunio_server fake_hardware --ros-args \
  -p serve_robot:=true \
  -p serve_measure:=false \
  2>&1 | tee "/tmp/tunio_web_reregister_fake_$(date +%Y%m%d_%H%M%S).log"
```

마이크 서버는 제공하지 않는다. **재등록에는 마이크가 필요 없다는 계약**을 확인하는 구성이다.

## 5. 터미널 C — 서비스·상태 확인

2절 공통 환경 설정 후:

```bash
ros2 service type /tuning/reregister_pegs
ros2 action info /robot/register_peg
ros2 action info /robot/return_home
ros2 action info /audio/measure_pitch
```

기대값:

- 서비스 타입: `tunio_interfaces/srv/CommandTuning`.
- register_peg와 return_home의 Action 서버 각각 1개.
- measure_pitch는 서버 0개 또는 해당 Action을 찾을 수 없음.
- 로봇 Action 서버가 2개 이상이면 다른 실행이 섞여 있으므로 먼저 정리한다.

상태를 계속 보고 싶으면 다음을 실행한다. 종료는 Ctrl+C다.

```bash
ros2 topic echo /tuning/state tunio_interfaces/msg/TuningState \
  --qos-reliability reliable --qos-durability transient_local
```

웹 버튼 시험 전부터 구독한다. 직전 상태 한 건만 보고 완료 여부를 판단하지 않는다.

## 6. 웹 재등록 성공 시험

관제의 ‘작업 이력’에서 기존 건수를 먼저 확인한 뒤 ‘실시간 작업’으로 돌아온다.
‘페그 재등록’을 한 번 누른다. 기타를 튕기거나 페그를 직접 돌릴 필요는 없다.

기대 순서:

1. 요청 중에는 중복 클릭 차단.
2. 접수 응답과 등록 상태를 수신한다. `accepted=true` 자체는 완료가 아니다.
3. 서버가 현재 STRING_ORDER 순서로 재등록한다. 기본은 6→5→2→1.
4. 대기 자세 복귀 후 `phase=0`, 빈 job_id로 돌아온다.
5. 웹에 ‘페그 재등록·복귀 완료 — 시작을 눌러 조율하세요.’ 안내가 남는다.
6. 시작/재등록 버튼을 다시 사용할 수 있다.

**가짜 로봇의 RegisterPeg·ReturnHome은 즉시 성공하므로 단계가 매우 빨리 지나간다.**
모든 줄을 눈으로 보지 못했다고 실패는 아니다. 터미널 A의 줄별 등록 요청·성공·복귀 완료 로그를 확인한다.
`prepare_delay_sec`는 발현 준비 지연이며 재등록을 느리게 만들지 않는다.

터미널 A에서 확인할 문구:

```text
6번 페그 각 등록 요청
5번 페그 각 등록 요청
2번 페그 각 등록 요청
1번 페그 각 등록 요청
페그 재등록·복귀 완료
```

추가 확인:

- 마이크가 없는데 재등록이 성공한다.
- 측정·발현·조절 단계로 넘어가지 않는다.
- ‘작업 이력’을 새로 읽어도 재등록으로 새 조율 결과가 추가되지 않는다.
- 완료 판정은 조율 성공 배지가 아니라 별도의 재등록 안내다.

웹이 ‘완료 경로를 확인하지 못했습니다’라고 표시하면 터미널 로그와 화면을 보존한다.
중간 상태 누락을 성공으로 추정하지 않도록 만든 안내다.

## 7. 웹을 거치지 않고 서비스만 분리 확인

작업이 끝난 대기 상태에서만 터미널 C로 실행한다. 웹 버튼과 동시에 요청하지 않는다.

```bash
ros2 service call /tuning/reregister_pegs \
  tunio_interfaces/srv/CommandTuning '{}'
```

접수 응답 뒤 터미널 A의 완료 로그를 확인한다.
**CLI에서 요청한 회차는 웹이 직접 접수한 회차가 아니므로 웹 전용 완료 안내가 뜨지 않을 수 있다.**
따라서 웹 버튼 시험 성공 여부는 6절 방식으로 판단한다.

## 8. 일반 조율과 재등록 실행 배제 시험

터미널 B의 fake_hardware만 Ctrl+C로 종료한다. 공통 환경이 유지된 같은 터미널에서 마이크 대역까지 켠다.

```bash
ros2 run tunio_server fake_hardware --ros-args \
  -p serve_robot:=true -p serve_measure:=true \
  -p mode:=on_target \
  -p prepare_delay_sec:=5.0
```

1. 관제에서 ‘시작’을 누른다. 준비 단계에서 약 5초 기다리므로 버튼 상태를 볼 여유가 있다.
2. 조율 진행 중 ‘페그 재등록’과 ‘시작’이 비활성인지 확인한다.
3. 일시정지 후에도 재등록 버튼이 비활성인지 확인한다. 단계 경계까지 기다릴 수 있다.
4. 이때 터미널 C에서 7절 서비스 요청을 보내면 `accepted=false`, 진행 중인 작업이 있다는 사유가 나와야 한다.
5. 재개해 완료시킨다. 완료 뒤 다시 재등록할 수 있는지 확인한다.

이제 일반 조율을 실제로 실행했으므로 이력에 조율 결과가 추가되는 것은 정상이다.
재등록 회차의 무저장과 구분한다. fake의 주파수·조절 성공은 실제 음질/조율 성능의 증거가 아니다.

## 9. 새로고침·연결 끊김·실패/취소 확인 범위

- 대기 중 새로고침만 해도 재등록 완료가 새로 표시되면 안 된다.
- 터미널 A를 종료하면 웹이 연결 끊김을 표시하고 조작 버튼을 비활성화해야 한다.
- 다시 같은 명령으로 기동해 상태를 받으면 조작이 가능해진다. 단절만으로 이전 재등록 성공을 만들어내면 안 된다.
- 가짜 등록·복귀가 즉시 끝나므로 재등록 중 수동 취소·일시정지·중간 단절은 재현하기 어렵다.
- `mode:=fail`은 **오디오 실패 설정**이며 등록 실패를 만들지 않는다.
- 등록 오류/취소/응답 전 상태 도착/복귀 누락 처리는 자동 시험으로 확인했다. 실물에서 일부러 충돌·케이블 분리로 오류를 만들지 않는다.

자동 시험 재실행:

```bash
export ROS_DOMAIN_ID=194
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
unset ROS_DISCOVERY_SERVER ROS_SUPER_CLIENT
colcon test --executor sequential --packages-select tunio_server
colcon test-result --test-result-base build/tunio_server --verbose
```

웹 상태 추적 시험은 Node.js가 설치된 환경에서:

```bash
node src/tunio_server/test/test_registration.js
node src/tunio_server/test/test_web_error.js
```

이 PC의 일반 셸에는 Node.js 실행 명령이 없을 수 있다. 이번 개발 검증은 별도 Node VM으로 실행했다.
ROS 테스트는 colcon으로 수행한다. 테스트용 도메인 194에는 다른 노드를 실행하지 않는다. 실행 중인 대역과 동일 도메인으로 검사하면 Action 응답이 섞일 수 있다.

## 10. 실물 확인으로 넘어갈 때

1. 대역 노드와 시험 서버를 모두 종료한다.
2. 웹 변경이 커밋/배포된 뒤 관제·로봇 PC에 동일 인터페이스를 빌드하고 노드를 재시작한다. 이 PR 브랜치를 받아야 웹 기능이 포함된다.
3. 기존 실물 통합 도메인/Discovery 환경과 드라이버 기동 절차를 사용한다.
4. 관제는 station.launch.py, 로봇은 robot.launch.py dry_run:=false로 현장 담당자가 기동한다.
5. 기타·로봇 준비를 확인한 뒤 ‘페그 재등록’을 누른다. 실제 6→5→2→1 등록과 복귀가 끝나는지 확인한다.
6. 성공 후 사람이 별도로 ‘시작’을 누른다. 일반 시작에서 유효한 등록값을 재사용하는 것은 정상이다.

강제 재등록은 각 줄 요청 시 해당 줄의 이전 각도를 무효화한다. 실패한 줄의 이전 값은 복원되지 않는다.
취소/일시정지는 즉시 물리 정지를 보장하지 않는다. dry_run은 실제 각도 파일을 바꾸지 않으므로 실제 등록 검증과 구분한다.

## 12. 로봇·마이크 없이 “먼저 등록하세요” 안내 시험

터미널 A는 3절 관제 서버(8090)를 유지한다. 기존 터미널 B의 fake_hardware는 Ctrl+C로 종료하고, 2절 환경 설정 후 아래로 다시 켠다.

```bash
ros2 run tunio_server fake_hardware --ros-args \
  -p serve_robot:=true -p serve_measure:=true \
  -p require_peg_registration:=true -p mode:=on_target \
  -p prepare_delay_sec:=1.0 -p play_delay_sec:=0.1 \
  -p ready_delay_sec:=0.1 -p measure_delay_sec:=0.2
```

1. http://localhost:8090 에서 등록 전에 **시작**을 누른다.
2. 시작 접수 후 준비가 실패하며 화면에 **“6번 페그 등록값 없음 — 페그 재등록을 먼저 실행하세요”**가 포함된 오류 안내가 남아야 한다. 실제 대상 첫 줄이 변경된 설정이면 해당 줄 번호가 나온다.
3. 새로고침해도 오류 사유가 표시되어야 한다. 이때 자동 등록·발현·측정·조율 결과 저장은 하지 않는다.
4. **페그 재등록**을 누른다. 기존 오류 안내가 지워지고 등록·복귀 완료 후 대기가 된다. 재등록만으로 조율 이력이 늘어나지 않는다.
5. **시작**을 다시 누른다. 자동 등록을 반복하지 않고 준비→발현→측정 순서로 진행한다. 가짜 주파수는 목표값이다.
6. fake_hardware만 재시작하면 메모리 등록 상태가 사라진다. 다시 시작하면 미등록 안내가 재현되어야 한다. 실제 로봇의 디스크 캐시 동작과는 다르다.

`require_peg_registration` 기본값은 false로 기존 대역 시험을 유지한다. true일 때만 줄별 메모리 등록 상태를 검사한다. 실제 등록 파일을 지우지 않으며 실물 경로·접촉은 검증하지 않는다.

### “없는 명령: reregister_pegs”가 뜬다면

8080에 예전에 실행한 web_node가 남아 있는지 확인한다. 새 HTML은 읽었어도 실행 중인 Python 서버는 옛 코드일 수 있다. 이 가이드의 주소는 **8090**이다. 코드 빌드 후 해당 시험 서버를 Ctrl+C로 종료하고 source·재시작하며, 브라우저는 Ctrl+Shift+R로 갱신한다.
