# docs/robot_data — 로봇 도구가 남기는 원자료

`tools/` 의 도구들과 `tunio_robot.runlog` 가 실행할 때마다 자동으로 쌓는다.
파일명은 `<날짜>_<시각>_<이름>.json` 이다. **사람이 손으로 만들지 않는다.**

성공한 측정만 있는 게 아니다. 실패·진단 회차도 그대로 남는다.
나중에 원인을 되짚을 때 필요해서다.

## 2026-09-22 피크 집기·발현 좌표 조정

정묵이 피크 집기·발현이 잘 됨을 실기로 확인했다. 앞서 집기→발현→반환
3회 동작도 확인했으나, 최종 좌표로 10회 연속 성공하거나 전체 통합을 완료한
기록은 아니다. 자동 파지 감지는 없으며 성공 여부는 작업자의 관찰이다.

`teach_points.yaml` 변경값 (Base 좌표, TCP `GripperDA_v1`, 단위 mm):
- `pick.holder.x` Z: 172.0 → 164.0. 집기·반환 공용.
- `pluck.6.x` Z: 182.28 → 187.70.
- `pluck.5.x` Z: 182.18 → 187.70.
- `pluck.2.x` Z: 181.78 → 187.70.
- `pluck.1.x` Z: 181.32 → 187.70.
- `pegs.2.x` Z: 109.0 → 108.0. 함께 조정됐지만 이번 발현 시험으로 검증된 값은 아니다.

원자료는 `2026-09-22_*_pluck_session.json` 27개다. 전부 6번 줄 요청이며,
23개에 발현 1회, 4개에 발현 0회가 기록됐다. 로그에는 사용 좌표·파지 성공·반환
성공이 저장되지 않으므로, 이 숫자를 성공률이나 최종 좌표 반복 검증으로 쓰지 않는다.

테스트 도구는 거치대 위 높이를 50mm로 덮어쓰지만 실제 노드는 YAML의 200mm를
사용하며 발현 대기 자세도 다르다. 실제 Action 경로·4줄 측정·조율 수렴은 통합에서
따로 확인한다. `pluck_session.py`에는 첫 대기 자세 도착 후 그리퍼 열기를 추가했다
(`--no-pick`이면 생략).

## ⚠️ 믿으면 안 되는 진단 문구

### "손잡이가 서 있어 그리퍼가 못 들어간다" — 거짓이다

해당 파일: `2026-09-21_152107_peg_register.json`, `2026-09-21_154200_peg_register.json`

```
"들어가다 막혔다 (Y 축 2.0N). 손잡이가 서 있어 그리퍼가 못 들어간다.
 그 페그를 손으로 눕힌 뒤 다시 시도하라 (#31)"
```

**그리퍼는 허공에 있었다.** 진입 판정에 쓰던 `check_force_condition(axis, max=2.0)`
이 "2N 을 넘었나" 가 아니라 **"2N 이하인가"** 를 묻는 범위 검사였다. 허공은 0N 이니
**항상 참**이 되어, 진입을 아예 하지 않고 막혔다고 보고했다.

PR #37 이 이 API 를 걷어내고 2단 진입으로 바꿨다. 그 뒤 회차는 정상이다.

이 문구를 믿고 손잡이를 눕히는 쪽으로 시간을 썼다. **진단이 구체적일수록 더 잘
믿긴다** — "막혔다" 보다 "손잡이가 서 있다" 가 훨씬 위험했다. 문구 옆에 측정값을
같이 찍는 것이 유일한 방어다. 저 줄에 실제 Y 축 힘 `0.0N` 이 같이 있었으면
바로 보였을 것이다.

### "토크로 파지를 가릴 수 있다" — 부정됐다

해당 파일: `2026-09-19_120000_turn_peg6_loosen.json`,
`2026-09-21_113201_turn_peg6_loosen_air.json`

`peg_turn_check` 가 찍는 그 판정을 믿지 말 것. 허공 회차와 파지 회차의 회전 중
토크가 구분되지 않는다(차이 0.023, 흩어짐 0.11). 근거와 경위는 CLAUDE.md 3.6.

- `2026-09-21_151623_peg_register.json` — "빈손이다 (폭 15.1mm)" 는 **맞다.**
  폭 판별은 Modbus 실측이라 신뢰할 수 있다

  빈손 13.0 / 물림 19.6 / 사점 28.9~32.8mm. 사점만 회차 간 3.9mm 차이가 난다
