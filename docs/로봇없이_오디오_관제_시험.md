# 로봇 없이 USB 마이크와 관제 서버 시험하기

작성: 2026-09-23. 현재 저장소 코드와 런치를 읽고 작성했다.
현재 수정본의 실행 안내서다. 네 줄 순서는 6→5→2→1이다.
아래 실행 명령은 사용자가 직접 실행하는 절차다.

## 1. 앞서 무엇을 바꿨나

### 녹음이 중간중간 잘리던 문제

- 파일: `src/tunio_audio/tunio_audio/recorder.py`
- 이전: 마이크가 넘겨준 소리에서 요청한 0.1초만 가져오고 나머지는 버렸다.
- 변경: 남은 소리를 보관했다가 다음 0.1초 읽기에 이어 붙인다.
- 이유: 중간이 빠진 파형은 주파수와 안정성 판정을 흐트러뜨린다.
- 새 측정을 시작할 때는 이전 측정의 남은 소리를 비운다.

예를 들어 44100Hz·512샘플 블록으로 재현했을 때 읽기 사이에 198샘플이 빠졌다.
샘플 유실 결함은 확인했지만, 실제 통합 당시 블록 크기와 원음이 없어 모든 실패의
원인이 이것 하나라고 확정한 것은 아니다.

### 성공한 줄만 마지막에 다시 검사

- 파일: `src/tunio_server/tunio_server/task_manager.py`
- 이전: 1차 실패 줄도 검증해 실패 사유가 바뀔 수 있었다.
- 변경: 1차 성공 줄만 검증한다. 실패 줄의 사유와 이전 측정값은 그대로 둔다.
- 따라서 2번이 중간에 측정 실패했다면, 마지막에 ‘검증 시 틀어짐’으로 덮어쓰지 않는다.
- 성공한 줄이 검증에서 실제로 틀어지면 기존처럼 검증 실패로 판정한다.

### 설정·테스트·문서

- `src/tunio_audio/config/audio_params.yaml`: 과도음 제외 0.3→0.5초.
  노드 기본값은 이전 커밋에서 이미 0.5초였다. YAML도 맞춘 것이다.
  `station`과 `sim_robot`은 이 YAML을 직접 읽지 않으므로, 이번 변경으로
  두 런치의 과도음 제외 시간이 새로 달라지는 것은 아니다.
- `src/tunio_audio/test/test_recorder.py`: 샘플 연속성과 새 측정 시 초기화 테스트 추가.
- `src/tunio_server/test/test_verify.py`: 실패 사유 보존과 성공 줄의 검증 테스트 추가.
- `src/tunio_server/test/test_prepare.py`: 네 줄 등록 테스트 안에서만 네 줄 순서를 지정.
  현장용 두 줄 설정 때문에 기존 네 줄 테스트가 깨지지 않게 했다.
- `src/tunio_server/tunio_server/tuning_logic.py`: 내가 추가한 것은 빈 줄 하나다.
  처음에는 사용자 설정 `[2, 1]`을 유지했고, 이후 요청으로 `[6, 5, 2, 1]`로 복원했다.
- `CLAUDE.md`, `docs/TUNIO_INTERFACE_SPEC.md`: 성공 줄만 검증하는 정책 반영.
- `docs/오디오_통합실패_2026-09-23.md`: Git 이력·첨부 로그·재현 실험 정리.

앞선 작업에서 오디오 25개 + 서버 66개 = 91개 테스트와 두 패키지 빌드는 통과했다.
실제 로봇 통합 재시험은 하지 않았다. 실행 시점의 PR 상태는 GitHub에서 확인한다.

**변경하지 않은 것:** 돌출도 20dB, 창 일치 12센트, 탐색 범위 ±2반음,
로봇 동작. 타임아웃 추천안도 아직 적용하지 않았다.

## 2. 이번 시험 구성

기존 `sim_robot.launch.py`를 쓴다.

```text
사람이 기타 줄을 튕김
        ↓
USB 마이크 → 실제 audio_analyzer → 실제 task_manager → 실제 관제 웹·DB
                                      ↕
                          fake_hardware가 로봇 응답만 대신함
```

마이크가 가짜가 되는 `sim_all.launch.py`와는 다르다.
`station.launch.py`만 켜면 서버가 로봇 Action을 기다리므로 로봇 없는 시험에는 부족하다.
`sim_robot`은 페그 등록·발현·복귀에 가짜 성공 응답을 주어 서버 흐름을 이어 준다.
실제 소리는 반드시 사람이 내야 한다.

## 3. 준비

1. USB 마이크를 연결한다. 지금처럼 USB 마이크가 OS 기본 입력이면 `device:=-1`을 쓴다.
2. 기타를 마이크 가까이 두고 다른 줄은 손으로 살짝 뮤트한다.
3. 마이크 노이즈 제거·자동 게인·에코 제거를 꺼 둔다.
4. 이전 station·sim_all·audio_analyzer 실행 터미널이 있으면 종료한다.
5. 이번 시험은 아래처럼 별도 ROS 도메인을 사용한다. 예시 77은 로봇 PC에서 사용하지
   않는 번호여야 한다. 모든 시험 터미널에 같은 번호를 설정한다.

기존 통합 환경으로 돌아갈 때는 새 터미널에서 원래 ROS 도메인·Discovery 설정을 사용한다.

### 터미널 A — 환경 준비

```bash
cd /home/rokey/tunio_ws
source /opt/ros/jazzy/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=77
unset ROS_DISCOVERY_SERVER
```

앞선 작업에서 수정본은 이미 빌드했다. 같은 PC·같은 작업 폴더라면 곧바로 4절로 간다.
다른 PC에서 소스를 가져왔거나 이후 코드를 바꾼 경우에만 다음을 실행한다.

```bash
colcon build --packages-select tunio_interfaces tunio_audio tunio_server tunio_bringup
source install/setup.bash
```

마이크 목록만 확인하고 싶다면:

```bash
python3 -m sounddevice
```

입력 레벨도 확인하고 싶다면 런치를 켜기 전에 아래를 실행한다.
명령은 입력 장치를 차례로 녹음하므로 장치 수에 따라 시간이 걸린다.

```bash
python3 tools/mic_level.py --duration 2
```

목록의 특정 장치만 보려면 예를 들어 `--device 2`를 추가한다.
**2는 예시 번호다.** 기본 입력이 이미 USB라면 런치에 번호를 억지로 지정할 필요 없다.
mic_level의 레벨 판정만으로 주파수 분석 성공을 보장하지는 않는다.

## 4. 관제 + 실제 마이크 + 가짜 로봇 실행

터미널 A에서:

```bash
ros2 launch tunio_bringup sim_robot.launch.py \
  device:=-1 \
  port:=8080 \
  db:=/tmp/tunio_audio_only_test.db
```

시험 결과는 `/tmp/tunio_audio_only_test.db`에 저장한다. 기존 실기 DB와 분리되며,
이 파일은 재부팅이나 임시 파일 정리 시 사라질 수 있다.

브라우저에서 다음 주소를 연다.

```text
http://localhost:8080
```

8080 포트가 사용 중이면 `port:=9000`으로 실행하고 `http://localhost:9000`을 연다.

로그에서 확인할 것:

- `audio_analyzer`: 입력 장치 열림, `/audio/measure_pitch` 대기.
- `fake_hardware`: **로봇을 대신한다**는 메시지. 마이크는 실제 audio_analyzer가 담당.
- `task_manager`: 현재 줄 순서 `[6, 5, 2, 1]`.
- `result_store`: 시험용 DB 경로.

## 5. 관제 설정과 사람이 튕길 타이밍

시작 버튼을 누르기 전에 **설정** 탭에서 다음을 입력하고 **저장**한다.

- 최대 조절 횟수: **0** — 이번에는 페그를 돌리지 않고 측정만 한다.
- 측정 재시도 횟수: **3** — 실패 시 추가 3회, 최초 포함 최대 4회.
- 허용 센트: **10.0** 유지.
- 측정 제한 시간: **10.0초** 유지.
- onset 제한 시간: **10.0초** 유지.

이번에는 사람이 바로 튕길 수 있어 10초로 시작한다. 실제 로봇의 약 22초 준비 동작과는
별개 시험이다. 기각된 잡음 때문에 측정이 일찍 끝나는 기존 정책 자체는 아직 남아 있다.

시험 순서:

1. 화면에서 **시작**을 누른다. 가짜 로봇의 페그 등록이 끝나면 측정이 시작된다.
2. 터미널 A에서 다음과 같은 줄을 기다린다.

   ```text
   [job ... / 6번 / m1 / 목표 82.41Hz] 준비 완료 — onset 대기
   ```

3. 준비 완료를 본 뒤 약 0.5~1초 후 **6번 줄만 한 번** 튕긴다.
4. 2~3초 정도 울리게 두고 결과를 기다린다. 분석 도중 연속해서 튕기지 않는다.
5. 다음 `준비 완료 — onset 대기`가 뜨면 그 줄 번호를 보고 다시 한 번 튕긴다.
6. 1차 성공한 줄은 마지막 검증에서도 다시 요청되므로 한 번 더 튕긴다.
7. 작업이 끝나면 기록에서 주파수와 실패 사유를 확인한다.

가짜 로봇의 ‘발현 성공’ 메시지가 실제 소리를 내 주지는 않는다.
판단 기준은 **audio_analyzer의 준비 완료와 줄 번호**다.
현재 코드는 6→5→2→1 순서다.

### ‘주파수 분석 성공’과 ‘조율 성공’은 다르다

예를 들어 2번 줄이 240.84Hz로 안정적으로 측정되면 **분석은 성공**이다.
하지만 목표 246.94Hz와 차이가 크고 최대 조절 횟수를 0으로 뒀으므로,
작업 결과는 **조절 횟수 소진**으로 실패할 수 있다. 분석 고장으로 해석하지 않는다.

반면 로그가 `후보 기각 — 돌출 부족`, `창 불일치`라면 유효 측정으로 채택되지 않은 것이다.
화면의 작업 성공/실패만 보지 말고 실제 Hz와 분석 로그를 함께 확인한다.

## 6. 코드 변경 없이 6·5번까지 개별 분석하기

관제의 네 줄 순회 대신 원하는 줄만 따로 분석하려면 같은 런치를 켜 둔 채
아래 명령으로 분석 Action만 직접 호출할 수 있다.

**관제 작업이 완전히 끝나거나 시작 전 대기 상태일 때만 실행한다.**
관제의 시작 버튼과 이 명령을 동시에 사용하지 않는다.
이 방법은 터미널에서 분석 결과를 보는 시험이며 관제 화면·DB에 해당 결과를 넣지는 않는다.
관제에서 시작하면 현재는 6·5·2·1번을 모두 순회한다.

### 터미널 B — 같은 환경 준비

```bash
cd /home/rokey/tunio_ws
source /opt/ros/jazzy/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=77
unset ROS_DISCOVERY_SERVER
```

한 명령을 실행하고 `ready: true` 또는 터미널 A의 준비 완료를 본 다음 해당 줄을 튕긴다.
결과가 나온 뒤 다음 명령을 실행한다. 명령 네 개를 한꺼번에 붙여 넣지 않는다.

6번 E2:

```bash
ros2 action send_goal /audio/measure_pitch tunio_interfaces/action/MeasurePitch \
  '{job_id: manual_audio, string_number: 6, measurement_id: 1, target_hz: 82.4069, timeout_sec: 10.0, onset_timeout_sec: 10.0}' --feedback
```

5번 A2:

```bash
ros2 action send_goal /audio/measure_pitch tunio_interfaces/action/MeasurePitch \
  '{job_id: manual_audio, string_number: 5, measurement_id: 2, target_hz: 110.0, timeout_sec: 10.0, onset_timeout_sec: 10.0}' --feedback
```

2번 B3:

```bash
ros2 action send_goal /audio/measure_pitch tunio_interfaces/action/MeasurePitch \
  '{job_id: manual_audio, string_number: 2, measurement_id: 3, target_hz: 246.9417, timeout_sec: 10.0, onset_timeout_sec: 10.0}' --feedback
```

1번 E4:

```bash
ros2 action send_goal /audio/measure_pitch tunio_interfaces/action/MeasurePitch \
  '{job_id: manual_audio, string_number: 1, measurement_id: 4, target_hz: 329.6276, timeout_sec: 10.0, onset_timeout_sec: 10.0}' --feedback
```

성공 예시(숫자는 예시):

```text
success: true
frequency_hz: 82.5
failure_reason: 0
```

같은 줄을 10번 정도 반복해 성공 횟수와 측정 Hz를 기록하면 재현성을 보기 좋다.
반복할 때 `measurement_id`를 5, 6, 7…처럼 늘리면 로그 구분이 쉽다.

## 7. 결과를 읽는 법

- `success: true`: 유효한 주파수 측정. 목표에 맞게 조율됐다는 뜻은 아니다.
- `failure_reason: 1`: 입력이 약하거나 onset을 찾지 못한 경우 등. 상세 로그를 확인한다.
- `failure_reason: 2`: 유효 주파수를 판별하지 못함.
- `failure_reason: 3`: 시간 초과. 앞서 어떤 후보가 왜 기각됐는지 함께 본다.
- `돌출 부족`: 목표 대역 피크가 주변보다 충분히 뚜렷하지 않음.
- `창 불일치`: 같은 녹음의 여러 구간에서 주파수가 충분히 일치하지 않음.

실패하면 우선 마이크 위치·다른 줄 공명·주변 잡음·발현 시점을 확인한다.
줄 음정이 목표 ±2반음 밖이면 정상적인 줄 소리여도 채택되지 않을 수 있다.
돌출 기준을 바로 낮추지는 않는다. 로봇 구동음을 주파수로 오인한 이력이 있다.

이 시험에서 잘돼도 로봇 발현·구동음·피크 왕복 타이밍까지 검증된 것은 아니다.
다만 실제 녹음 경로와 분석기, 서버, 관제 연결이 정상인지 먼저 분리해서 확인할 수 있다.

## 8. 종료와 문제 확인

시험이 끝나면 터미널 A에서 Ctrl-C로 런치를 종료한다.
종료 시 `rcl_shutdown already called`가 나올 수 있는데 기존 종료 처리 문제다.
측정 중 기각 원인과 구분해서 본다.

노드 구성 확인(터미널 B, 같은 도메인):

```bash
ros2 node list
ros2 action info /audio/measure_pitch
ros2 action info /robot/play_string
```

이 구성에서는 각 Action 서버가 하나씩 있어야 한다.
마이크는 audio_analyzer, 로봇은 fake_hardware가 담당한다.
서버가 둘이면 이전 런치나 실제 로봇 노드가 같은 도메인에 남아 있는지 확인한다.

로그를 파일로도 남기고 싶다면 다음 시험 시작 때 4절 명령 대신 아래를 사용한다.

```bash
ros2 launch tunio_bringup sim_robot.launch.py \
  device:=-1 port:=8080 db:=/tmp/tunio_audio_only_test.db \
  2>&1 | tee /tmp/tunio_audio_only_test.log
```

로그에는 줄 번호, 후보 기각 이유, 측정 Hz, 돌출도, 창 일치 값이 포함된다.
로그 파일은 같은 명령을 다시 실행하면 덮어쓰므로 보관할 회차는 다른 이름으로 복사한다.
